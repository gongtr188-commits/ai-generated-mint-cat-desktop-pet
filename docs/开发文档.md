  开关关 —— 站着没事 71.1% · 打瞌睡 7.2% · 趴着驻留 6.8% · 坐着 5.9% · 走动 7.6% · 拥抱 1.4%；
  开关开 —— 站着没事 68.9% · 趴着睡 7.0% · 打瞌睡 5.0% · 四足爬走 4.9% · 坐着 4.1% · 趴着 3.8%。
  用户一碰就安静 6 秒，不抢操作（`tools/behavior_check.py`，12 种子 × 2 小时 × 两档开关）
- **走还是跑她自己决定**：一趟行程按走路的步子要超过 7 秒就自动换成**跑步态**
  （实测约两成漫游会升级）；菜单上"向左走/向右走"永远只是走，要跑点"跑向远处"。
  趴着没有跑的素材，所以四足爬走不会被升级
- **驻留姿态是"姿态 × 朝向"两个正交维度**：坐下 / 打瞌睡 / 趴着 / 趴着睡 各是一个姿态，
  各自的朝向表与转身调度器（站立环形 360°、趴着线性 180°、其余只有一个朝向走 `InstantTurn`）。
  驻留期间播哪一段微动可以是**按朝向对齐的列表**（趴着只有正面那段会动；左右躺睡各一段）
- **「左右趴着」开关（默认关）只管"趴着时能不能侧过去"**：`prone_left`/`prone_right` 两个朝向、
  `prone_turn`、要用这两套朝向加四足步态的**四足爬走**，以及**左右躺着的趴着睡整个姿态**。
  **正面趴下与打瞌睡是常驻动作，不问开关**。关掉时四道一起落：菜单入口消失、
  `start()` 挡、在飞的睡姿起身、排队的意图作废（§13.17③）
- **跟随鼠标（默认关）**：勾上之后她**一小步一小步**朝光标走（死区 40px、>260px 换跑），
  到跟前就停、保持行进方向；菜单开着不跟、姿态驻留期不跟、跟随期间随机池完全让位（§13.17⑪）
- **姿态可以连着点**：趴着期间点"坐下"以前是**静默没反应**，现在进意图队列，
  她起身之后自动接上坐下（最多等 3 秒，等不到作废，免得几十秒后突然自己坐下）
- **不能玩（素材够但代码未接）**：声音、双形象、道具
- **画布是横向的 896×768**：坐姿/趴姿在同一机位下比站姿宽得多，
  所以窗口不再是正方形，滑条调的是高度、宽度按比例派生。
  归一是**双约束**（身高 660 与 内容宽 848 取小），所以横躺的睡姿实际只有 513~554 高
- **只有正面有静立素材**，所以呼吸仅在正面站姿出现；侧面/背面静止时仍是静态姿势
- **验证**：`tools/smoke_test.py` **350 项**断言全过（含 **529 组**动作两两串联
  + 300 条随机长链；纯逻辑单测若干 + 素材层回归锁：抠图碎块 / 涂白回吃 /
  源画面裁切 / 步态相位 / 转身图顺序 / **派生静姿图与源帧逐字节相同** /
  **任何一段动画都不许贴到画布左右缘**）；
  `tools/calibrate_turn.py --strip` 出转身胶片图目视确认无多余帧；
  `tools/strip_check.py` 出**每段动画的逐帧深色胶片**，面积偏离中位 >12% 的帧自动标红；
  `tools/source_check.py` 是新素材到货的第一道体检（帧数/背景/漂移趋势/步态周期/贴边裁切），
  `向左走_四足` 那条废素材就是被它量出来"角色出画 + 根本没有步态周期"的；
  `tools/jitter_check.py` 用"方向翻转率 × 屏幕像素摆幅"两个条件一起判抖；
  `tools/render_check.py` 出**浅底／品红底／深色底**三张拼图——深色那张是唯一能看见

## 3. 关键决策与理由

### 3.1 素材规格先于代码（菲比 §3.2 的直接照搬）

统一画布 **768×768**，内容按**高度**归一到 `CHAR_H=660`，底部对齐、基线留 `24`，水平居中。

- **为什么 768 而不是刚好装下的 712**：当前最宽素材内容 706 px，只留 6 px 余量。
  后续动作素材（伸懒腰、扑人、甩尾）必然更宽，画布重定 = 全量重建 + 重新目视校验，
  成本远高于现在多留 60 px。
- **为什么按高度而不是宽度归一**：见 §3.2 的实测。
- **带来的红利**：窗口尺寸直接等于画布尺寸（`resize_to_pet()` 就是 `setFixedSize(h, h)`），
  不用为每张素材单独算宽度和偏移，素材天然对齐。

### 3.2 背面"看起来大一圈"的真凶是归一化维度选错（v0.1 唯一一次返工）

用户反馈背面素材偏大 24%。第一轮管线**误按宽度归一**（`span()` 里 `sum(axis=1-axis)`
写反了），导致背面内容 613×660 → 修好后仍然 613×660，但视觉观感从"太大"变成"太小"。

用视频做交叉验证（视频整段共用同一缩放，是天然的"同一角色不同朝向"真值）：

| 朝向 | 视频帧面积 | 视频 w×h | 静帧归一后 w×h | 静帧/视频 宽度比 |
|---|---|---|---|---|
| 正面 f000 | 318 807 | 670×627 | 706×660 | 0.875 |
| 背面 f060 | 265 093 | 586×629 | 613×660 | 0.868 |

视频里背面 = **同高、窄 12.6%、面积少 17%**；静帧高度归一后 = 同高、窄 13.2%、面积少 12%。
两法吻合 → **高度归一正确，`POSE_K.back = 1.0`，不做补偿**。

> 结论：`docs/preview/back_k_probe.png` 里背面 x1.12 "看着更协调"是错觉——
> 一旦给背面加倍率，v0.2 接上转身动画时就会在背向那几帧出现尺寸跳变。
> 观感协调性由视频（真实旋转）裁决，不由静帧并排裁决。

### 3.3 抠图：边缘种子泛洪 + 最大连通域

角色有白色绒毛、背景也是白（实测 252~255），纯色键必抠穿。管线两步：

1. 从**四边**泛洪浅色区算背景，被毛边围住的白色（肚皮、耳内绒毛）保留
2. 前景只留**最大连通块**

第 2 步能清掉**与角色不相连**的碎块，但清不掉压在她毛上的那部分水印（相连 → 属于最大连通块）。
v0.2.4 补了定向清除，见 §10.5。

### 3.4 色调对齐：整段动画共用一个增益

实测青毛均值：正面 90/209/226（基准）、左 90/212/229、右 93/215/230、背 99/221/235，
**视频整段 94/194/205**——比静帧暗 8~11，直接播转身会在转身瞬间"跳色"。

处理：以正面图为基准，其余素材按 `strength=0.5` 温和靠拢（菲比同值）。
视频用**全段均值算一个增益**套到每一帧，绝不逐帧算——逐帧参考色会随帧漂移，看起来就是闪烁。
实测视频增益 `0.978 / 1.038 / 1.050`，处理后与静帧一致。

### 3.5 朝向语义（菲比在这里返工过，一开始就定死）

`manifest.faces = ["front", "side_left", "back", "side_right"]` → facing 四分位 0/1/2/3。

**`side_left` = 素材里脸朝画面左 = 向左走时用**。命名和用途同向，不需要菲比那种
"向左坐要用右侧身素材"的镜像换算。素材文件名 `薄荷猫猫_左面.png` 直接对应，无歧义。

### 3.6 Qt 插件路径兜底不是可选项

本机 Python 装在中文路径（`D:\手动配置\python\...`），`QLibraryInfo.location(PluginsPath)`
返回 `D:/????/python/...`，`QApplication([])` 直接静默死掉（连报错都没有，极难定位）。
`app.ensure_qt_plugins()` 必须在创建 QApplication **之前**调用；`tools/` 下的脚本同样要调。

菲比项目打包 PyInstaller 时踩的是同一个根因（它的坑 27），届时解法是把 PyQt5 复制到纯
ASCII 目录并设 `PYTHONPATH`。

### 3.7 为什么模块化而不是单文件

菲比主张单文件（状态机/素材/交互互相引用）。薄荷（猫猫）从 0 开始且明确要长期扩，
所以按职责拆 8 个模块，每条都有独立可验证的边界：

| 模块 | 单一职责 | 依赖 |
|---|---|---|
| `config` | 数值 | 无 |
| `manifest` | 素材清单解析 + 变体回退 | config |
| `assets` | 读盘 + 缩放 + 缓存 | 无（纯 Qt 图像类） |
| `facing` | 朝向与转身调度 | config（**不 import Qt，可脱离 GUI 单测**） |
| `behavior` | 走路 / 爬走 / 跟随 / 随机池 | config（`Walker`、`Crawler`、`Follower` 都**不碰 Qt**，光标坐标由宿主注入） |
| `stage` | 窗口 / 尺寸 / 绘制 / tick | 上面全部 |
| `interaction` | 鼠标 / 菜单 | stage 的字段（mixin） |
| `app` | 引导 | 全部 |

`facing.py` 刻意不依赖 Qt：转身关键帧表、路径去重、选边逻辑是本项目将来最难返工的模块
（菲比返工 5 轮），能脱离 GUI 直接跑断言才压得住。

## 6. 已知问题与取舍

| # | 现象 | 原因 | 处理 |
|---|---|---|---|
| 1 | 单击换朝向有约 80 ms 延迟 | `InstantTurn` 在下一帧 tick 才落地 | 故意保留：让 `TurnDirector` 从一开始就是异步语义，`VideoTurn` 才能零改动替换 |
| 2 | 窗口比素材宽，边缘留约 5% 透明 | 统一画布的必然结果 | `content_rect()` 已提供内容矩形，v0.2 坐窗/贴边按它算留白 |
| 3 | 左右侧身素材宽度差 12%（699 vs 622） | 源图右侧身尾巴收在身下、左侧身甩在外面 | 不改。改了转身会跳 |
| 5 | 转身最后一帧从视频帧切到静态姿势图有极轻微跳变 | 视频帧与静帧本来就是两次生成（side_right 最近帧与静帧的灰度差 8.4，约等于 1.6 个正常帧步） | 接受。要消除得用视频帧当 idle 姿势，但静帧清晰度高得多，不划算 |
| 6 | 转身在飞时接到新的 `turn_to`，**上一调用者挂着的 `done` 会被顶掉** | `VideoTurn.start` 直接重写 `self.done` | 语义本身保留（被打断的一转不该兑现完成契约），但**任何依赖 done 的状态机都必须自己兜底** —— 曾经因此让行程永久卡在 `returning`。见 §12.8 |

## 7. 下一步（v0.9 建议顺序）

1. **侧面 / 背面的待机微动** —— 现在只有正面会呼吸，转到侧面就"死"了。
   漫游之后这条更突出：她到达时会转回正面（有呼吸），但用户手动停在侧面就是张静图。
   **需要新素材：静立_左面 / 静立_右面 / 静立_背面**
   （或者让 `IdlePlayer` 支持按朝向各挂一个动画，素材到位即可接）
2. **重做 `向左走_四足`**（唯一还挂着的素材缺陷）—— 要求**角色在画面里保持居中、
   不许平移**（`向右走_四足` 漂移只有 14px 所以是好的）。现素材从第 72 帧起她整个人
   走出画面左缘，脸被切掉，且**没有步态周期**所以截前缀也救不了。见 §13.9。
   在此之前**四足开关保持默认关**。
   ~~坐下素材的白色光晕~~ 已在 v0.9 用相对容差泛洪修掉（§11.13），不用再换素材。
3. **趴着的过渡素材** —— 现在"正面趴下"是硬切静帧（`PostureHold` 的 `enter=None` 分支），
   补一条 `趴下_过渡` 视频就能和坐下一样有起卧。状态机不用动。
4. **自发行为继续扩充** —— 池子已有 roam / sit / prone / crawl 四种（权重与冷却都在
   `config.BEHAVIOR_WEIGHTS`），**每加一个动作只需一个状态机 + 一行权重**：
   伸懒腰、舔爪子、被摸头反应。
5. **景深缩放** —— 既然整个屏幕都是地面，"越靠上越小"能让漫游的立体感一下成立，
   而且不需要任何新素材。代价是她看起来会比尺寸滑条给的数值小一点，得想清楚交互。
6. ~~**带目的的行程**~~ —— v0.12 交付过 `trips.py`（`edge_sit` / `visit_mouse`），
   **v0.14 按用户要求删掉了**："把移动的坐下和找鼠标删了"。
   这两条的语义被「跟随鼠标」覆盖得更直接，而且它们与"移动"子菜单的分组原则冲突（§13.17⑩）。
7. 声音（需要新素材）
8. 头顶小黑猫发夹作为可拆卸道具（需要新素材：无发夹版 4 朝向）
9. exe 打包发布 —— `assets/` 现在是 **1590 个散帧 PNG、共 601 MB**（最大单文件 0.55 MB，
   **不存在** GitHub 单文件 100 MB 问题）。要处理的是"这些文件跟着 exe 走"：
   打 zip 或装到用户目录，别让首启动去解 1590 次盘。
   另注意项目路径含中文会撞菲比坑 27（§3.6）。

> **v0.12 用户已明确不做的**：景深缩放、伸懒腰/舔毛/被摸头反应（后者还要新素材）。
> 挂在这里只是为了别再被当成"下一步"提出来。

## 9. 转身标定（v0.2，本项目最难的一块）

菲比为了转身返工 5 轮（"多帧"→"还是有几帧多余"→"转多了"→"绕远转到正确方向了"），
所以这里从一开始就用数据标定，**不在代码里试帧号**。

### 9.1 三件套与它们的分工

| 方法 | 产出 | 作用 |
|---|---|---|
| 相邻帧视觉差异 | `path[]` 累计视觉进度 | 把"帧号"换算成"角度进度"，是另外两法的基础 |
| 参考距离法（每帧 vs 4 张标准姿势） | `keys[]` 四朝向关键帧 | **定值**：朝向到底对应哪一帧 |
| 路径比例法（累计进度 1/4、1/2、3/4 圈） | 交叉校验值 | **抓数量级错误**，允许偏差（起步慢、到位有停顿） |

`keys` 由管线在入库时算好写进 manifest，`calibrate_turn.py` 只做复核，**不维护第二套值**。

### 9.2 标定抓到的两件事

**① 视频尾部有 23 帧冗余正面静止帧。** 视频长 121 帧，但 360° 在第 98 帧就转完了
（`d0[i] <= max(2.0, 0.1*max(d0))` 自动检测）。若按 121 帧做循环，转身起手会先原地顿
1.8 秒才开始动——菲比"转多了 / 有多余画面"的根因就是这个。`cycle` 只取真正转完的那一段。

**② 转身严重不匀速。** 一圈 98 帧里四个 90° 分别占 **27 / 18 / 23 / 30** 帧。
所以不能把帧号 4 等分当朝向，也不能按帧号等分采样。

### 9.3 采样：按帧号等分 → 按累计视觉路径等分

第一版照菲比文档写的是"帧号等分 + 平台区去重阈值"。实测 `back→side_left`
按帧号等分出来的 9 帧里，前 4 帧几乎一模一样（视觉变化全挤在后半段），
观感就是"点了一下没反应，然后突然转过去"。

改成**按 `path[]` 等分**：先沿行进方向累出每一步的视觉变化，再按等分值反查帧号。
停滞区里累计进度不推进，采样点自然撞车、被去重掉——**连平台区阈值都不需要了**，
`TURN_PLATFORM_DIST` 直接删掉。

量化（12 个方向对，"最慢一步变化 / 平均一步变化"，越接近 1 越匀速）：

| 采样方式 | min | p25 | 中位 |
|---|---|---|---|
| 按帧号等分 | 0.22 | 0.43 | 0.45 |
| 按累计路径等分 | **0.47** | **0.70** | **0.80** |

### 9.4 中途改道必须从"正在显示的那一帧"出发

`_pos()` 第一版写的是 `seq[self.i]`，但 `i` 在 `tick()` 里已经自增，那是**下一帧**。
拿它当改道起点会让新序列凭空跳过一帧，表现为转身上手一顿。
必须用 `self.shown`（最后真正画出来的那一帧）。这个 bug 是冒烟测试
"转身中途改道从当前帧就近出发"抓出来的。

同理，`spin()` 的目标沿用**在飞那一转的朝向**：用户先点"背面"再点"转一圈"，
他期待的是转完停在背面，而不是就近停下或退回起点。

### 9.5 跨环区间的视觉距离不能取 min/max

平台判定早期写成 `lo, hi = min(a,b), max(a,b)`，于是跨越 cycle 末尾的那一小段
被算成"绕整圈"的补集，永远判定为"有明显变化"，去重**静默失效**（不报错、只是没效果）。
必须按行进方向算跨环距离。现在的路径采样里这一步收敛进了 `_step()`。

## 10. v0.2.2 三处返工（用户实机反馈驱动）

### 10.1 菜单点朝向项必崩：延迟回调捕获了菜单拥有的对象

**症状**：右键 → 朝向 → 左侧身/右侧身，桌宠直接消失。不是异常，是**整个进程 abort**
（退出码 0xC0000409），连 Python 堆栈都没有。

**定位过程**：先写 13 条路径的压力复现（四朝向、连点改道、转圈中途改朝向、
转身中途换尺寸/切置顶/移动窗口/切变体）——**全 OK**。说明崩溃不在转身逻辑里，
而在我绕过去的那条路上：`menu.exec_()`。

最小复现只剩一行差异，做对照实验：

| 实验 | 唯一变量 | 结果 |
|---|---|---|
| drop | `del menu` | **EXIT=127，硬 abort，无输出** |
| keep | 多留一个 `pet._menu_ref = menu` | EXIT=0，朝向正常改变 |

**根因**：`build_menu()` 建的是**无父对象的 QMenu**，`show_menu()` 只把它放在局部变量里，
`exec_()` 一返回就被 C++ 析构。而朝向项的回调按 §10.3 的规矩用 `_later()` 推到菜单关闭
之后再执行 —— 那时 `a.data()` 解引用的是已经销毁的 QAction，PyQt 直接 abort。

只有朝向项会崩，因为其他项捕获的是 int / 布尔 / `self`（`退出` 直连 `QApplication.quit`，
`回到右下角` 只捕获 `self.place_default`），都不依赖菜单拥有的对象。

**修法**：定一条不变式并写进 `_later()` 的文档串——
**延迟回调只准捕获 int / 布尔 / self，绝不捕获菜单拥有的 QAction 或 QWidget**。
朝向项改成在菜单还活着时就把 `data()` 取成普通 int，再交给延迟回调。

**回归锁**：`smoke_test.py --menu-child` 子进程跑完整生命周期并断言退出码。
必须用子进程，因为这类崩溃是 C++ 层 abort，混在主套件里会把后面所有测试一起带走。

### 10.2 转身帧白边：h264 振铃，用轮廓内收治

**先量化再动手。** 第一版指标（`10 < alpha < 245` 的羽化环带）测的是错的东西——
它量的是 alpha 过渡带，而白边的本体是**不透明的近白像素**。换成
"亮度 >215 且紧贴背景的前景像素"这个口径后：

| 素材 | 亮边占前景面积 |
|---|---|
| 视频帧 | **0.91 ~ 0.95%** |
| 静帧 | 0.09% |

差 10 倍，确认白边是视频帧独有的。成因：h264 在高对比的暗描边外圈甩出振铃亮斑
（mosquito noise）；这些像素亮度够但通道极差超标，泛洪不收，又紧贴描边所以属于最大
连通块，于是留了下来。

**中间走过一次弯路**：先尝试收紧泛洪判据（`BG_MIN`/`BG_SPAN`），实测发现源图背景
本来就极干净（亮度 248、通道极差 2.1），判据根本不是瓶颈——取样带选粗了才会得出
"覆盖 8~27%"这种没意义的数字。

**最终修法**：轮廓内收 `CHOKE=2`（形态学腐蚀）。扫内收量得到的数据：

| 内收 | 视频帧亮边 | 静帧亮边 |
|---|---|---|
| 0px | 0.91~0.95% | 0.09% |
| 1px | 0.33~0.36% | 0.00% |
| **2px** | **0.09~0.12%** | 0.00% |

2px 正好让视频帧回到静帧未处理时的水平，所以取 2。放在 `foreground()` 里而不是
`to_canvas()`，是为了让高度/面积/色调**所有测量和渲染共用同一张掩膜**，否则归一化会差出这 2px。

配套还做了两件事：
- **半透明环带的 RGB 回填最近前景色**（`distance_transform_edt` 的 index 模式）。
  源图边缘本来就是"深色描边 + 白底"的混合色，不回填的话羽化出来就是一圈浅色。
- **动画帧缩放前先转 `ARGB32_Premultiplied`**。非预乘下 `SmoothTransformation`
  会独立插值 alpha 与 RGB，在半透明边缘拉出亮边——这是运行时侧的放大器。

结果：环带 >200 占比 **16.34% → 1.57%**。残留的是描边外凸出的孤立小块，内收再大就要
吃进描边本体，不值得，记在 §6 已知问题 7。

### 10.3 转身颠簸 + 收尾弹跳：逐帧高度归一

之前"整段视频共用一个缩放系数"是**错的**。当时的理由是"逐帧各自归一会把转身变成
呼吸式脉动"，但实测数据推翻了它：

| 指标 | 值 |
|---|---|
| 周期内逐帧内容高 | 614 ~ 660，起伏 **7.3%** |
| 四个关键帧各自的高 | 626 / 615 / 628 / 644（**各不相同**） |
| 静态姿势的高 | 全部 660 |
| 底边 y 的 std | 0.45（稳） |
| 水平中心 x 的 std | 0.39（稳） |

共用缩放是按"最高的那一帧 = 660"定的，于是其余帧全都偏小；而原地转身的**真实身高
是不变的**，那 7.3% 纯属生成噪声。后果有两层：转动过程中她忽大忽小（颠簸），
且转身收尾从 ~620 弹到 660（大小不统一）。

**修法**：逐帧把内容高钉死到 `CHAR_H`。底边和水平中心本来就稳，不需要额外处理。
起伏 **7.3% → 0.3%**。

代价：素材里真实的透视收缩也被压平了。对原地转身这是正确的——她本来就不该变高。

### 10.4 静帧与动画的画风统一：锚点色彩矩阵（v0.2.3）

用户反馈"动画和静态图片的色调不一样"。这次不再用早期那个"青毛均值 + 单通道增益"的探针，
先把差异按明暗分段量出来：

| 区域 | 静帧 | 视频帧（校正前） | 差 |
|---|---|---|---|
| 青毛（中间调） | 92.6 / 213.9 / 230.7 | **146.3** / 224.5 / 232.9 | **R 差 53.7** |
| 白肚皮（高光） | 253.6 / 253.6 / 253.1 | 242.5 / 254.1 / 254.9 | R 差 11.1，且偏青 |
| 粉（饱和点缀） | 245.5 / 138.8 / 179.5 | 219.8 / 114.0 / 177.6 | R 差 25.7 |
| 暗描边（阴影） | 45.2 / 69.3 / 87.4（藏青） | 41.8 / 60.6 / 81.9（**红棕**） | 色相旋转 |

**关键判断：这不是"偏色"，是色相旋转 + 曲线压缩。** 证据是方向相反：
视频把中间调的 R **抬高**（92.6→146.3），同时把高光的 R **压低**（253.6→242.5）。
所以：

- 单通道线性增益（早期 `tone_gain`）修不好——按下葫芦浮起瓢；
- 逐通道 mean+std 双矩匹配能对齐亮度与对比，但**对齐不了色相**，
  实测把青毛从差 53.7 拉到 3~10，可暗描边仍然红棕、粉色仍差 14~16；
- 只有带交叉项的 **3×3 色彩矩阵**能做色相旋转。

**做法**：取四个锚点区域（青毛=中间调、白肚皮=高光、暗描边=阴影、粉=饱和点缀）各自的
平均 RGB，最小二乘拟合一个把视频锚点映射到静帧锚点的 3×3 矩阵。

三个必要的约束，少一个就会翻车：
1. **锚点必须跨明暗三段。** 只有 4 个锚点、9 个自由度，缺了阴影或高光矩阵就定不住。
2. **带单位阵方向的岭回归**（`ridge=0.35`）。不加约束的话，在锚点色域之外会外推出离谱的值。
3. **按 `TONE_STRENGTH=0.85` 与单位阵混合**，留 15% 给视频自身的立体明暗，不然转起来发闷。

**逐帧校正、基准固定**：每一帧单独算自己的锚点、单独解一个矩阵，但参考永远是静帧那一组。
菲比文档说的"色调参考固定取自同一张基准图"是针对**参考**的，不是针对**校正量**的——
这里正好用得上：视频转一圈本来就有明暗变化，逐帧解矩阵把它拉回同一套调色，
而参考不随帧漂移，所以不会闪。

实测校正后视频帧青毛 = **92.7 ± 0.6 / 210.6 ± 1.0 / 226.3 ± 0.9**（基准 90/209/226），
逐帧标准差小于 1，即整圈色调稳定。

**结果**（四朝向 × 四区域的最大通道差）：

| 阶段 | 全区域最大差 |
|---|---|
| 单通道增益（v0.2 及以前） | 53.7 |
| 逐通道 mean+std 双矩匹配 | 16.4（粉色） |
| 锚点 3×3 矩阵 | **7.2** |

`docs/preview/tone_pair.png` 是静帧与转身关键帧的并排图，肉眼已经是同一套调色。

**残留（治不了的部分）**：视频源只有 720px，静帧 1254px，放大到 768 画布后
**描边细节比静帧软**。这是分辨率与画师笔触的差异，色彩算法无能为力。
要彻底一致只能二选一：① 出更高分辨率的转身视频；② 反过来把静帧也做轻度柔化对齐。

### 10.5 水印清除的补漏：最大连通块不够，还得按连通性定向涂白

v0.1 我写过"水印与角色不连通，天然可分"，并用 `blobs=1` 当证据。**那个结论是错的**，
而且错在拿一个测不出问题的指标当证明：`blobs=1` 只说明"最后只剩一块"，
压在她毛发上的那部分水印本来就和她相连，自然跟着进了最大连通块。
用户实机看出来了：右下角"豆包AI生成"在若干帧仍然可见。

**定位方法**：先按颜色签名（低饱和中性灰、亮度 135~244）在全帧找候选块，
再看空间分布——水印是一条固定在 **x 0.806~0.992、y 0.925~0.978**（比例，不是像素，
换分辨率不用重标）的横带。逐帧统计确认 **121/121 帧都在**，中位 1201 个签名像素。

中间试过两个错路，都记下来免得重犯：
1. **时不变检测**（121 帧里从不变化的像素 = 静态叠加层）：失败。角色身体中心是大片
   平坦青色，转起来几乎不变，测出 18 万个"静态"像素，水印淹在里面。
2. **把整个框涂白**：危险。实测角色前景在 46/121 帧里压进了那个框，
   涂白会在她身上打穿一个洞。

**最终做法**：只在框内、只把**满足签名且能从框边连通到外部**的文字像素涂白，
再交给泛洪当背景吃掉。连通性这一步是关键——被毛发包住的文字如果也涂白，
泛洪从边界走不到它（四周都是前景），结果是在身体上留下一个**不透明的白洞**，
比原来的白边更难看。宁可留一点淡痕，不打穿主体。

水印是画在角色**之上**的叠加层，所以压在毛上的字会和她混色（饱和度升高 → 不满足签名），
这部分留着不动。实测带内残留：中位 **1201 → 11**，最大 62，视觉确认字样已消失
（`docs/preview/watermark_check.png`）。

顺带：清除水印改变了轮廓的测量结果，转身标定值随之更新
（cycle 98 不变，一圈视觉路径 647.4 → 622.2，交叉验证偏差从 7/3/7 收窄到 7/1/4）。

## 11. v0.3：待机呼吸、连点方向、白点点

### 11.1 两种动画必须用两种放置策略（这条最容易想当然）

新素材 `静立_正面.mp4` 接进来时，最省事的做法是照抄转身的管线。那样会把动画做废：

| | 内容高起伏 | 水平位移 | 正确策略 |
|---|---|---|---|
| 转身 | 7.3%（**噪声**：原地转身身高不该变） | ±0.4px（可忽略） | `per_frame` 逐帧归一到 CHAR_H |
| 静立 | 1.6%（**信号**：这就是呼吸） | ±3.6px（**信号**：这就是摇摆） | `sequence` 整段共用缩放 + 固定水平锚点 |

- 对静立做逐帧高度归一 → **呼吸被压平**，白做。
- 对静立做逐帧 bbox 居中 → **左右摇摆被抵消**，白做。所以 `sequence` 模式的水平锚点
  取全段 bbox 中心的**中位数**，让平均位置落在画布正中、而每帧相对它摆动。

实测静立输出帧高 656~664（起伏 1.21%）保留住了，冒烟里直接量输出帧断言
`0.4% < 起伏 < 3.0%`——不是只看 `mode` 标志位。

策略写在 `build_assets.ANIM_MODE`，产物里带 `mode` 字段，运行时不需要知道。

### 11.2 连点转身"先转又往回转"

**根因**：`cycle()` 每次调 `turn_to()` 都重新取最短路径。她在转 90° 的途中（约 0.4s）
你又点了一下，新目标的最短路径方向可能和当前旋转方向**相反**，于是就掉头。
连点四次正好累积成"转过去又转回来"，观感就是卡。

**修法**：`CLICK_CYCLE = [0,3,2,1]` 本身就是视频的前进方向，所以给 `turn_to` 加
方向提示参数 `hint`（0 最短 / ±1 强制），单击循环传 `hint=+1`。连点于是变成
**连续单向旋转**，点几下转几圈，符合直觉。

菜单直选保持 `hint=0`：用户明确改主意时不该绕远。

顺带修了游标同步：`apply()` 里把 `_cycle_pos` 对齐到当前朝向在 `CLICK_CYCLE` 中的位置。
之前从菜单直选过朝向之后再单击，会从游标残留处跳回起点。

冒烟锁死：连点 8 次（每 2 tick 改一次目标）全程步进都 ≤ 半圈、无一次倒退，
且两轮循环后回到起点朝向。

### 11.3 边缘白点点：判据要从"最大连通块"升级到"描边屏障"

v0.2.2 的轮廓内收 2px 只吃掉了贴边的一圈，**凸出较多的亮斑还在**，用户实机看到
"靠近边缘的白点点没抠干净"。

**走过的弯路**：先按"亮且低饱和的边界像素"计数，测出 316~917 个，看着像杂质——
但那个口径**分不清杂质和合法的白色绒毛边缘**（她耳内、肚皮本来就是白的）。
开运算也几乎无效（316→266），说明它们不是薄凸块。

**最终判据**：这套画风全身都有粗暗描边，所以**拿描边当墙**。对 `fg & ~墙`
做连通标记，凡与背景相邻的块都在描边之外 → 是杂质。

必须带**尺寸上限**：描边一旦有缺口，整片身体会连成一个"贴背景"的巨块，
无上限时 f080 的面积保留率直接塌到 **15.9%**（身体被当杂质删了）。
实测杂质最大 83px、漏块 194375px，`DEBRIS_MAX=400` 落在两者之间，
且 200~4000 结果完全一致 —— 这个阈值不敏感，是好事。

结果：转身 121 帧亮粒合计 **48275 → 100**（集中在描边有缺口的那一帧，84 个，
占该帧前景约 0.04%），静立 121 帧 **0**，四张静帧 **0**。

### 11.4 测试自身的两个坑（都是测试错，不是产品错）

值得记下来，因为这类"假故障"很容易诱导去改本来正确的代码：

1. 断言 `单击循环顺序 == [3,2,1,0]` 在加了游标同步之后失败，实测得到 `[1,0,3,2]`。
   这是**对的**——测试前面把她转到了背面，从背面继续正向就该是这个序列。
   断言改成按起点算期望。
2. 断言 `菜单直选走最短路径` 用 `seq[1] < seq[0]` 判方向，跨 cycle 末尾回绕时
   （1 → 94）裸索引反而变大。改成按**环上步进**判：每步 `(a-b) % cycle` 都 ≤ 半圈，
   且合计等于短路径长度（28）。
3. 待机断言用定长 `wait(90)` 等一个 80ms 的 tick，不保证真跑到 → `shown` 偶发为
   `None` 直接 TypeError。全部换成 `wait_until` 轮询。连跑 5 轮验证稳定。

### 11.5 静立与转身交接错位、尾巴被切（v0.3.1）

用户反馈两条现象：转身动画与正面静止动画"衔接不流畅、有点错位、没对齐"，
以及右下角尾巴被截掉一小部分。**同一个 bug 的两个症状。**

量出来的事实：

| 来源 | 内容中心 x | 底边 y |
|---|---|---|
| 静帧 front | 383.5 | 743 |
| 转身 f001 | 383.0 | 743 |
| 静立 f000（修复前） | **424.0** | 743 |
| 静立 f000（修复后） | 383.0 | 743 |

静立整体右移 **40px**，于是 `x1 = 767` 正好顶到画布右边缘 —— 尾巴被切掉，
而转身结束（383）交接给静立（424）时就是肉眼可见的一跳。

**根因**是 `to_canvas()` 的参数语义被用反了。它的 `anchor` 参与的计算是
`px = anchor - sw / 2`，其中 `sw` 是**该帧自己**缩放后的宽度。而 `build_anims`
传的是 `median(源bbox中心) × scale` —— 那是"源图坐标系里的中心位置"，
不是"画布上希望内容中心落在哪"。720 源图里角色中心约 366，乘缩放 1.1576 得 423.7，
就这么被当成了画布绝对坐标。

**第二个被掩盖的 bug**：就算锚点数值算对，`anchor - sw/2` 也等于把每一帧重新居中，
摇摆会被完全抵消。实测修复前静立 f000 与 f060 的中心只差 1px（本该差 3~4px）——
摇摆其实一直没渲染出来，只是被 40px 的整体偏移盖住了没被发现。

**修法**：把参数改成 `anchor_dx`，语义是**相对默认居中位置的偏移量**：
`px = (CANVAS_W - sw) // 2 + anchor_dx`，其中 `anchor_dx = (该帧源中心 − 全段中位中心) × scale`。
这样平均位置仍与静帧/转身帧重合，每帧又各自摆动。

修后实测：静立中心 379.5~387.0（均值 383.2，与静帧差 0.3px），
摆幅 ±3.2px 真的出来了，触边帧 0/121。

**回归锁**（7 项，加进冒烟）：每个动画都要过
①无任一帧触到画布四边 ②平均中心与静帧对齐 ±2px ③底边压在基线 ±1px
④摇摆幅度落在 1~12px 之间（为 0 说明又被居中抵消，过大说明锚点漂了）。

写锁的时候我自己把基线期望值算差一行：`paste` 之后内容**最后一行的索引**是
`768 − 24 − 1 = 743`，744 是第一个空行。测试失败暴露的往往是自己，不一定是产品。

### 11.6 待机倍速：先随机游走，再改成"每圈换目标 + 限幅逼近"

固定速度是机械感的主要来源，所以倍速要随机。但**第一版做错了方向**：
我用的是逐 tick 有界随机游走（`drift=0.06` + 朝中值回归）。看着"平滑"，
实际一圈 61 tick 内游走的标准差就有 ~0.30 —— 也就是**一圈之内就能从 0.5 抖到 1.0**。
用户一句"切速度倍率的时候最好平滑一点，相邻的两个不要差得太多"点破了：
随机的粒度选错了，逐 tick 抖等于忽快忽慢。

改成两件事分离：
- **每圈结束抽一个新的目标倍速** `target ~ U(0.5, 1.0)` —— 负责"有变化"
- **每 tick 最多向目标逼近 `IDLE_SPEED_RATE=0.012`** —— 负责"变化不突兀"

于是相邻两 tick 的倍速差被**硬上限**锁死（实测 max Δ=0.0120，均值 0.0021），
而从 0.5 走到 1.0 需要 42 tick = 3.3s，正好摊在接近一整圈（4.9s）的时间里，
听不出"换挡"这个动作，只看得出她有时呼吸浅一点、有时深一点。

`reset()`（转身结束、或从别处回到正面时重新入场）**保留当前倍速**，只把相位归零。
第一版在这里重抽了一次倍速 —— 那正好是用户最容易盯着看的时刻，会明显变调。

**一个测试窗口引起的假失败**：断言"倍速会走满区间两端"在 600 tick（约 10 圈）下
失败，实测只到 0.53~0.83。不是产品问题——限幅逼近天然收敛得慢，10 圈来不及把
速度推到两端。拉长到 3000 tick（49 圈）后覆盖 0.519~0.988。
随机类断言的窗口必须按"探索完区间需要多少圈"来定，不能凭感觉给个数。

### 11.7 `--only poses` 会抹掉动画登记（清单部分重建缺陷）

`build_assets.py` 每次都用当次的 `poses` / `anims` 重写整个 `manifest.json`。
所以 `--only poses` 会把 `anims` 写成空字典 —— 桌宠**静默退回静态姿势**，
不报错、不提示，只是转身和呼吸全没了。`--only anims` 同理会抹掉 poses 的 content 元数据。

修法：写盘前若旧清单存在，把本次没重建的那一半搬过来；色彩基准 `tone_ref`
也一并继承，`--only anims` 不必重新解一遍矩阵。

这类"部分重建抹掉另一部分"的坑，特征都是**坏掉的时候没有任何症状指向原因**，
所以文档和冒烟都要留一笔。加素材时如果只换了图片或只换了视频，
最省心的做法还是不带 `--only` 跑全量。

### 11.8 绕正面 vs 绕背面（v0.3.3）

用户要求：菜单让她在 左面/右面 之间切换时**要路过正面，别绕到背面去**——观众要看的是她的脸。
菲比文档 §4.6 有一模一样的坑（"到位那一转是绕背面，观感就是绕远"），解法也是同一个：强制方向。

先把 12 条转换的两条路径全列出来（环上顺序 front1 → side_right28 → back47 → side_left71）：

| 转换 | 正向 | 途经 | 反向 | 途经 | 最短选的是 |
|---|---|---|---|---|---|
| 左面↔右面 | 55 | **正** | 43 | 背 | 43 → 绕背面 ❌ |
| 背面→侧面 | 24 | 背 | 74 | 正 | 24 → 绕背面 |
| 侧面→背面 | 19 | 背 | 79 | 正 | 19 → 绕背面 |
| 正面→侧面 | 27 | — | 28 | — | 本来就在正面，无需绕 |

**关键判断：不能一刀切"永远走正面"。** 背面→侧面 走正面要 74 帧、直达只 24 帧，
比值 **3.08** —— 那才是真绕远，会把一个 90° 转身拉成 270° 长途。
而 左面↔右面 是 55 vs 43，比值 **1.28**，两条路角度上都是 180°，只是素材不均匀
（正面附近占的帧数多），所以绕行几乎不额外花时长。

**规则**：只有当"两条路一条经正面、一条不经"且 `经正面距离 ≤ 另一条 × 1.6` 时，才让给正面。
门限 `TURN_FRONT_RATIO=1.6` 正好落在 1.28 与 3.08 之间。

实测改后**只有 左↔右 两条被改写**（`左→右` 走 71→78→86→93→6→…，
`右→左` 走 28→21→17→13→6→…），背面↔侧面 四条全部保持 24/19 帧直达。
左↔右 两条路都是半圈，所以时长没变（仍 9 帧 ≈ 0.72s），只是中途看得见脸。

单击循环（`CLICK_HINT=+1` 强制同向）与"转一圈"不受影响——它们不走最短路径分支。

**又一次测试度量错误**（第三次了，值得警惕）：`max_step` 用 `(b-a) % cycle` 判步长，
反向步进拿到的是**补数**（47→42 算成 93 而非 5），于是三条正常路线被判"绕远"。
环上距离必须再取 `min(d, cycle - d)`。

### 11.9 走路接入（v0.4）

`behavior.Walker` 的编排是 **转向 → 步态+平移 → 复位朝向** 三段：

- **必须先转向**：直接横着平移会像滑冰。向左走先转到 `side_left`，向右走先转到 `side_right`。
- **走完要转回出发前的朝向**：否则用户会发现"她走两步就再也不看镜头了"。
- **速度随显示高等比缩放**（`pet_h / DEFAULT_H * WALK_SPEED`）：菲比文档 §5.1 的教训，
  模型放大后速度不变的话，动画会显得小碎步滑行。
- **撞屏幕边就地结束**，不弹回去。弹回去会和"走完转回原朝向"的编排抢方向盘。
- **拖拽立刻打断**（`walker.stop()`）：用户上手了就没有"走"这一说。

`tick()` 顺序是 `facing → walker → idle`。走路必须在转身之后推进才能拿到刚落地的朝向；
待机放最后并加了 `not walker.busy` 闸门，保证三个渲染源不会抢同一个 QLabel。

### 11.10 擦除向右走的生成瑕疵（"多出来的左手"）

用户报告：向右走有部分片段，肚皮右缘多伸出一小撮青色的"左手"，要求擦掉且**不许误伤其他内容**。

**定位过程走了三次弯路，都记下来：**

1. **时不变检测**（静态叠加层思路）完全不适用——那是找水印的，凸起是动的。
2. **对齐到画布中心后取时位中位轮廓**：第一次实现把对齐写错了（面积只差 1%、
   凸出最大 339px），数字看着"没有瑕疵"。修正对齐后凸出面积涨到 1406px，才看见真信号。
3. **肚皮右界之外的青色**这个看似锐利的判据，抓到的其实是**合法的辫子**
   （辫子就垂在肚皮右上方，静帧右面图里也有）。把两组候选帧放一起目视比对才分辨出来：
   中位轮廓判据抓到的是凸起，辫子判据抓到的是辫子。

**决定性线索是周期性**：把凸出面积按 `i % 24` 分组，得到
相位 23=1250、0=1320、22=946、1=656，**其余 20 个相位全部 <550**；
而向左走同一指标是 85~274 的平坦分布。也就是瑕疵每个步态周期固定出现一次、约 4 帧，
且只有向右走有——与用户描述完全吻合。

**擦除规则**：`ANIM_ERASE = {"walk_right": dict(period=24, phases=(22,23,0,1), dilate=3)}`
—— 只在这些相位上，把轮廓裁回时位中位形状（膨胀 3px 容差）。

三个刻意的设计：
- **只裁配置了的动画和相位**。非瑕疵帧也有 40~550px 的"凸出"，那是腿爪正常摆动，
  无条件全裁会削掉合法动作。
- **中位轮廓取自本次刚生成、尚未擦除的原始帧**。若从磁盘重读，第二次跑管线时
  已裁过的帧会拉低中位数，把凸起"洗白"成正常形状，判据静默失效。
- **`np.minimum(alpha, soft*255)` 只降不升**，保留原有软边，不重铺 alpha。

**安全验证**：把"会被擦掉的像素"标红叠回原图逐帧看 —— 红块精确落在凸起上，
前爪、辫子、脸、毛边、尾巴全部未受影响（只有底部轮廓有 1~2px 抖动）。
结果：相位 22/23/0/1 的凸出面积 946~1320 → **0**，全片最大从 1406 降到 641
（与向左走的 583 同级，即只剩正常运动）。共擦除 21 帧。

**测试时机错误一处**：`走路期间待机没有抢画面` 原本放在走路结束后断言，
那时待机恢复才是正确行为，等于没测。改成在 `walker.busy` 期间逐帧采样。

### 11.11 v0.4 的擦除没擦干净：两处判据缺陷（v0.5 返工）

用户实机反馈："还是有一点没扣干净"。v0.4 那版有两个错，都不是"再调调参数"能解决的：

**① 相位窗口开晚了。** 重新按相位量化，凸出面积是
ph19=51 / ph20=187 / **ph21=557** / ph22..ph1=已擦 / ph2=95~166，
也就是凸起从 ph19 起步、ph21 最大、一路拖到 ph2。而 v0.4 只擦了 (22,23,0,1)，
恰好把**最严重的那几帧留在窗口外**。当初"其余 20 个相位全部 <550"的结论没错，
但 550 这条线是我拿"擦除前"的四个相位量出来的，用它当门限等于自己给自己放行。

**② 羽化留了一圈半透明裙边。** 原实现 `np.minimum(alpha, gaussian(keep))`，
在裁剪线 `keep` 之外留下 alpha 20~128 的渐变带，每帧约 70 px。
而当时的验证脚本只数 `alpha > 128`，**这圈裙边正好在阈值以下**——
所以"凸出面积 → 0"的结论是真的，但它测的不是用户看到的东西。

**排除掉的一条路**：想用形态学开运算做"逐帧几何检测"（凸起 = 挂在光滑大轮廓外侧、
放不下半径 r 圆盘的小包），不再依赖猜相位。实测否掉：r=14 时凸起只被认出一个 31 px 的尖
（它太大、圆盘塞得进去），而同一判据在转身素材上误伤 67 px（发梢/耳尖）。放弃。

**最终规则**：`phases=(19,20,21,22,23,0,1,2)` + **只在 `roi=(640,495,720,615)` 内动手** +
**硬切不羽化**（`alpha[cut]=0`）。三条各治一件事：
- 加相位治 ①；
- 硬切治 ②；
- 限 ROI 是安全边界——中位形状是整段共用的，走路时手脚本来到处伸，
  全屏裁会削掉合法摆臂。ROI 取凸起实测活动范围（x663-687 / y527-588）外扩一圈。

**验证**：擦除前后同帧并排放大目视（`f21` 那一大坨没了、`f23` 的裙边没了、
`f18` 完全没动、合法轮廓没有缺口）；擦除帧数 21 → **41**；
凸起区"硬残留 / 半透明"逐帧统计 → **0 / 0**。
冒烟里加了回归锁：量落盘帧在 ROI 内超出"中位形状 + 3px"且 `alpha > 8` 的像素，
单帧必须 ≤20 px（实测 18）。**阈值特意含半透明**，否则又会被同一类裙边骗过去。

### 11.12 坐下素材的白色毛刺光晕：第一条判据试错了（v0.7 发现，v0.9 修好见 §11.13）

发现过程本身值得记一笔：**冒烟 198 项全绿、孤岛统计为 0**，缺陷是我把 v0.7 新素材
渲染到**深色底**上看图才看见的——她耳侧蝴蝶结外面糊着一圈锯齿状白边。
之前所有判据（面积、包围盒、连通块、`alpha>8` 残留）全是"和上一版比"，
没有一个问过"合成到真实桌面上长什么样"。这是 Q-11 那条教训的第四次应验。

**它是什么**（逐像素量过，不是猜的）：

| 对象 | 亮度中位 | 通道差中位 | 说明 |
|---|---|---|---|
| 源图背景 | 240 | 6 | |
| 光晕 | **237** | 6 | 就是背景，被 h264 压暗了 3 级 |
| 她的白毛 | **248** | 2 | 比背景还亮 8 级 |

泛洪判背景的条件是 `min(通道) > BG_MIN(235)`，光晕的 min 通道正好卡在 234——
差一级没被抓到，于是它留在前景里；又因为它紧贴描边、和身体连通，
"取最大连通块"和 `drop_debris` 都管不着。蝴蝶结的锯齿描边把一块块背景**围成孤岛**，
泛洪从四边进不去，才留下这圈毛刺。sitdown 每帧多算 2~4% 面积（单块最大 6283 px）。

> 补充（v0.9 胶片核对）：**孤岛统计只抓到断开的那 7 帧**，
> 逐帧胶片显示光晕在 sitdown **几乎每一帧都在**（连在蝴蝶结上没断开）。
> 也就是说"孤岛数"量的是这个缺陷的零头，别拿它当"光晕只有 7 帧"。

**试过的修法：拿暗描边当墙再泛洪一次。** 暗像素（含抗锯齿边，阈值放宽到 185）膨胀 2px
封住压缩缺口，从四边泛洪"非墙"区，走得到的地方不算身体。
`seal/lum` 扫了 6×3 组参数：`lum=110` 时 19/61 帧塌到 10~30%（墙有缝，泛洪灌进身体），
`lum=185` 时零塌、最差 95.7%，sitdown 砍掉 3.4% 且砍掉的均亮 237——**数字全对**。

**这条判据作废**，因为数字对而图不对：重建后目视，`walk4_left` 约 1/3 帧的**胸口与前腿
整块消失**（单帧少 4.8 万像素），是墙把身体内部一处浅色区判成了"泛洪可达"。
收窄成"只砍面积小且颜色像背景的块"也不成立——白毛亮度 248 高于背景 240，
颜色上根本分不开，实测被误判的白毛块 48626 px 与真光晕块 6283 px 之间没有安全间隙。

（保留这段记录，是因为它值两条教训：① 目视图是最后一道关，见 §11.13；
② "所有指标全绿"不等于修好了，改抠图判据必须同时看**新指标绿了**和**图对了**。）

### 11.13 光晕最终是这么修掉的：泛洪判据改成"相对本帧背景色"（v0.9）

用户提示"是不是要看看技术文档"，回头读菲比 §3.3，发现它的泛洪用的是
**相对容差 `FLOOD_TOL=8`**，而我们写死了绝对阈值 `min(通道) > BG_MIN(235)`。
这正好解释了光晕为什么漏网：它就是背景，只是被 h264 压暗到 min 通道 234，
**差一级落在绝对阈值之外**。改成"离本帧自己的背景色足够近"就自然落网。

背景色取**四边 6px 环的中位**（素材规范保证角色不贴边，这一圈一定是背景）。

判据换完逐帧实测 610 帧：

| 素材 | 面积变化 | 孤岛（>400px 的断开块） |
|---|---|---|
| sitdown | −7.4%（掉的就是光晕） | **8 块 → 0 块** |
| 其余 7 段 | 最差 −0.33% | 0 → 0 |

深色底成品图上她耳侧那圈锯齿白毛刺**完全消失**，蝴蝶结、绒毛、发夹本体一个没少。
她的白毛(248)同样落在"离背景 8 级"以内、照样被判成可通行浅色，
之所以没被吃掉，靠的还是"泛洪只能沿与四边连通的区域走、而白毛被暗描边围住"——
**这一点新旧判据完全一致**，改的只是"哪些像素算可通行的背景"。

### 11.14 改对一处判据，会连带掀出两个藏在旧行为里的假设（v0.9）

光晕修好后，同一轮里连续暴露两个 bug。它们都不是新逻辑写错了，
而是**旧逻辑一直靠那个错误行为侥幸成立**：

**① 水印涂白填的是写死的纯白。** `scrub_watermark` 把水印笔画涂成 `255`，
旧的绝对判据（`>235`）能吃掉它；新的相对判据下 255 离背景 246 差 9 级、**落在容差之外**，
于是涂过的地方变成一块边缘整齐的纯白矩形留在成品里（深色桌面非常刺眼）。
修法：填色改用同一个 `bg_color(rgb)`，与泛洪认的色同源，**按构造就不可能再脱钩**。
另加自检 `scrub_leak` = "涂掉的像素里最后仍属前景的最大值"：
配套错误时实测 转身 2417px / 坐下 4633px，合法残留（笔画被毛发包住）只有 47px，
门限取 300。这条锁的意义是把"两个各自正确的模块配套错了"这类错误变成可检出的。

**② `settle_index` 的"全段最低点"一直靠光晕撑着。** 光晕把开头几帧的高度人为撑高，
反而盖住了"素材开头她先站起来挺直了"这个事实；光晕一去掉，内容高曲线变成
`f0 646 → f5 679 → f28 648`（先升后降），"全段最低点"当场退化成 **0**——
等于没有过渡动画，她会直接瞬移进坐姿。
判据改成"**先找峰，再找峰之后的最低点**"（坐定 = 下坐到底，物理含义就是它），
`settle` 回到 28。冒烟加了一条 `8 ≤ settle_at < 帧数-8` 的锁，专门抓这种退化。

顺带一条同族的：`walk4_right` 的接缝是相邻帧差的 11 倍（素材 97 帧不是整数个 22 帧周期），
以前没人管，现在管线会把步态循环截到整数个周期（→ 88 帧）。见 §13.10。

## 12. 随机行为与全屏漫游（v0.5 / v0.6）

用户要求三件事，按时间先后："桌宠最好加上随机动作"、"走路不要只是一个动画播完就停止，
随机一点"、"她可以在屏幕上随便走动，随机选取一点并走过去"。

### 12.1 结构：状态机 + 调度器

`behavior.py` 里 `Walker` 是一个 `phase` + `tick()` 的状态机，
`BehaviorPool` 只负责**挑**和**拦**。全部由 stage 那唯一的 80ms tick 驱动，
不开线程、不用 `QTimer` —— 这样任何状态都能被测试逐 tick 推进（见 12.7）。

`tick()` 顺序是 `facing → walker → idle → behaviors`。
行为池必须排在最后：它要看到前面所有状态机这一帧落地后的样子，否则同一 tick 里会重复触发。

> 中途加过一个 `Gazer`（东张西望：转到随机朝向、停一会儿、转回来），
> 用户看完直接否掉了："东张西望就算了"。原因很实在 ——
> 作为**自发**动作，她突然转头盯着墙看，观感更像 bug 而不是可爱；
> 而且这个能力单击换朝向已经有了。已整体删除。

### 12.2 全屏漫游：转成侧视朝向，斜着走过去

`Walker` 从"走一个固定方向 N 秒"改成**一个目标点 + 两轴同时推进**：
横向照常播侧视步态，纵向按斜率比例同步带一点位移，两轴**同时到达**。

- **目标点先过 `_legal()` 夹进可用区**（已扣任务栏）。这一步做完之后，
  "撞屏幕边"就从主流程退化成了安全网。
- **到达后转身面向镜头**（`home=IDLE_FACING`）。这是"我回来啦"的收尾，
  比转回出发朝向讨喜；菜单里手动的"向左走/向右走"仍回到出发朝向。

**单趟要限时长，不是限距离。** 第一版不限，逐 tick 录轨迹实测一趟 9~22 秒；
加上冷却算下来她**近一半时间在走路** —— 那不是"偶尔溜达"，是停不下来。
现在 `ROAM_MAX_S=8`，实测均 6.9s、最长 8.2s，占空比降到约 16%。

一段行程会把 121 帧的步态循环重复好几遍，所以先量了接缝：
末帧→首帧的视觉差 向左走 0.9x / 向右走 0.7x **于**正常相邻步进的中位数
（预乘 alpha 后比，避免把透明区当纯黑）。也就是循环点恰好是整段里最平的一步，
重复播放不会跳帧 —— 不需要为此做淡入淡出。

### 12.3 纵向没有步态素材，怎么办

素材只有左右两套侧视步态，没有"朝镜头走 / 背镜头走"。

**第一版做的是合成步伐起伏**：纵向段转成 背面（向上）/ 正面（向下），
窗口 y = 逻辑位置 + `amp·sin(2πt/period)`。为此还推了一条约束 ——
要读出"在走"，起伏的最大上升速率必须超过每 tick 位移，
即 `amp · 2·sin(π/period) > speed`。第一版取 `period=8, amp=3, speed=2`，
左边只有 2.30、和 2 几乎打平，逐 tick 记 y 序列发现**单调下降、一次反弹都没有**，
起伏被彻底淹没等于没做；改 `period=4` 后才翻出 73 次上升。

用户直接给了更好的方案：**"向上下某个点走，直接用向左右走的斜线移动过去就行了，
不用正面或背面上下移动"**。于是起伏、`_step_y`、`WALK_BOB_*` 整套删掉，
换成横向迈步时按比例带纵向位移 —— 侧视小人斜向移动本来就成立，比"竖着爬"自然得多，
而且不再需要任何新素材。

代价是**斜率必须有上限**（`WALK_SLOPE=0.45`，另有 `ROAM_MAX_DY=150` 兜底）：
再陡就不像走路了。纵向够不着时按斜率夹掉，**宁可到不了那个点**，
也不把身子拧成一个不像走路的角度。纯纵向的目标直接拒绝。

### 12.4 三层节流，各治一种"看着烦"

| 层 | 参数 | 治什么 |
|---|---|---|
| `hold` | 1.2s | 动作收尾后再占一会，治"做完立刻再做"的抽搐感 |
| `cd` | roam 12 / sit 25 / prone 25 / crawl 15s | 每类动作独立冷却，治"整屏就在那走来走去" |
| `quiet` | 6.0s | 用户刚点过/拖过/开过菜单就闭嘴，治"我在拖窗口她非要抢着转身" |

外加一条**连做降权**：`pick()` 给"上一轮那个"乘 `BEHAVIOR_REPEAT_PENALTY=0.35`，
避免加权随机连续五次都在走路。**是降权不是踢出候选** —— 踢出在候选只剩两类时
等于强制交替，权重完全不参与结果（这条是 v0.11 查出来的，全过程见 §12.9）。
`cd` 也**从收尾开始算**，且必须短于 `GAP` 的中位数，否则冷却会替权重做决定。
还有一条**快速重试** `BEHAVIOR_RETRY_S=1.5`：挑中了却没做成（贴边、全在冷却）时
不该为一次空手再等上一整段 12~40 秒的空闲。

`note_user()` 的接线点：鼠标按下、以及 `show_menu()` 的前后各一次
（菜单是阻塞事件循环，开着的那几秒她还在 tick，不按住就会在用户挑选项时自己走开）。

### 12.5 撞墙判定：只准查前导边

原来的写法每 tick 同时查左右两条边：

```python
if pet.x() <= screen_left or pet.x() + width >= screen_right:  # 两条边都查
```

用户报告"靠近屏幕边框有一小段区间，向远离的方向走也会判定停下"。
逐 tick 复现（贴边 0 / 5 / 40 px，往远离方向走）**没能复现出提前停止**——
三种距离都走满了全程。原因是那几 tick 撞墙条件确实为真，但她还在 `turning`，
`walker.tick()` 提前 return 才没执行到判停。**属于侥幸**。

改成只查**正在走向**的那条边，并把目标点先夹进可用区。
差分测试锁住：同参数下"贴左墙向右走"和"屏幕中间向右走"必须走得一样远。

顺带修掉两个同源问题：
- **零长度段会凭空平移**：`target == cur` 时 `dirn` 被算成 `-1`，
  而 `_past` 对 `-1` 的判据是"已经越过"，于是第一 tick 就把坐标硬改成 target。
  现在 `_next_leg()` 会跳过零长度段，并加了一条不变式：
  **任何一 tick 的位移都不许超过一步**。
- **`roam()` 抽样取点会偶发发起不了**：改成斜着走之后，"纵向至少走 `ROAM_MIN_PX`"
  经斜率反推出横向下限约 156px，再叠加时长上限 300px，可行域被压成 `|dx| ∈ [156,300]`
  一条窄带。全屏均匀抽样 + 六次重投，实测 seed=4 直接发起失败。
  现在**按约束直接构造**目标点（先挑有余量的方向，再在可行带里取 dx、按比例取 dy），
  不靠碰运气。约束变窄时抽样法会静默退化，构造法不会。
- **纵向段途中被外力挪动会跳回原位**：`set_size()` 是按底边重排窗口的，
  而 `_step_y()` 下一 tick 会把 y 写成旧的 `base` —— 她当场弹回去。
  现在记住上一 tick 真正写进窗口的 y，发现对不上就以窗口为准重新对齐逻辑位置。

### 12.6 一个自己把自己锁死的 bug

第一版 `tick()` 写成：

```python
busy = self.busy()                       # busy() 里含 hold
if self._busy_prev and not busy:
    self.hold = HOLD                     # "从忙转闲"的下降沿
self._busy_prev = busy
```

而 `busy()` 把 `hold` 自己也算进去了。于是：动作结束 → 设 hold → 下一 tick `busy()`
仍为真 → 再下一 tick hold 减到 0，`busy()` 又变假 → **下降沿再次成立 → 再设 hold**。
hold 无限续期，池子被自己设的占位永久锁死，**一个自发动作都发不出来**。

修法是把两层判定拆开：`actors_busy()`（只看执行者）负责抓下降沿，
`busy()`（含 hold）只负责拦触发。

这条 bug 是"跑 60 分钟看 fired 会不会持续增长"的回归锁抓出来的。
在此之前所有断言都是绿的——因为**没崩**和**没动作**在观察上长得一模一样。

### 12.7 随机系统怎么测

随机性不能靠"跑一次看看"。做法是**注入固定种子 RNG**，然后把断言下推到统计量上：

- 倍速/步程：200 次抽样要求出现 >50 种取值，且 min/max 锁在配置区间；
- 不重复：跑 40000 tick 收集触发序列，断言相邻两项不等、两种动作都轮到过；
- 互斥：每一 tick 都先记录 `busy()` 和 `fired`，断言"忙的那 tick 不许涨 fired"（累计违规数 == 0）；
- 节流：安静期 / 冷却 / hold / 快速重试各自单独造场景，包括"hold 会到期"这一条；
- 贴边：把假桌宠摆在 x=0 和 x=1360，200 次 `_pick_dir()` 必须只给朝内的方向；
- **差分**：同参数下"贴左墙向右走"与"屏幕中间向右走"必须走得一样远——
  直接断言位移会写成个拍脑袋的阈值，差分不需要；
- **不变式**：漫游全程逐 tick 记坐标，断言任一 tick 位移不超一步。
  这条抓到了零长度段导致的凭空平移，而那类 bug 用"到没到终点"是测不出来的；
- 纵向：数 y 序列的上升次数，起伏被速度淹没时（第一版）这里直接是 0。

`FakePet` 只实现行为状态机用到的最小接口（`x/y/move/width/screen_left/top/...`），
所以这 36 项完全不开 Qt，跑起来是毫秒级。

**两条踩过的坑，记下来免得再犯：**

1. `FakePet.tick()` 里带着 `BehaviorPool`，导致"走完自动转回出发朝向"这类
   单动作测试跑到一半被池子插进来一段漫游，测的已经不是被测对象。
   现在假桌宠**默认关闭池子**，只有池子自己的用例用 `pool_pet()` 显式打开。
   真实 `PetWindow` 同理：`main()` 一建好就关掉自发行为。
2. 开关类断言必须**先验"开"再验"关"**。只验"关掉后不动"，
   那么默认值一改就会让这条断言白给 —— 它当时确实就是这么假通过的。

### 12.8 动作串联矩阵：单动作断言永远测不到的一类缺陷

用户报"向右走的过程中回到右下角，位置会错位"，并要求"再检查一下还有没有多个动作
连起来才出现的 bug"。于是加了 `smoke_test.interaction_matrix()`：
**12 个动作两两组合穷举 144 组**，外加 **300 条随机长链**（3~8 步，一半开着自发行为），
每步检查一组不变式：位置在可用区内、窗口正方且等于 `pet_h`、朝向在 0~3、
非正面不许播待机、内容不溢出窗口、最终必须能回到静止。
全程手动 `pet.tick()` 驱动，不走事件循环，所以完全可复现。

**一次抓出 4 个真缺陷**，全都是"只在串联里出现"的：

| # | 现象 | 根因 |
|---|---|---|
| 1 | 走途中点"回到右下角"，她又朝旧目标走回去（实测 +25px，真实屏幕上是几百 px） | 目标点是**出发时算的绝对坐标**，人一旦被挪走，那个点就成了别人的位置 |
| 2 | 走途中**拖到左上角**，她接着朝旧目标走出 476px | `stop()` 只处理 `walking`，漏了"转身在飞、还没迈步"那段 |
| 3 | 走途中改尺寸，她**越界 193px**；撞边早停还多冲 1px | 目标点没有按当前窗口尺寸重夹 |
| 4 | **永久卡死**在 `returning`：不走路、不呼吸、不再自发行动 | 见下 |

第 4 个最严重，也最能说明为什么必须做串联测试。链路是
`向右走 → 单击循环 → 菜单转正面 → 拖到左上`：
`Facing.turn_to(q)` 不带 `done` 时会把**上一个调用者挂着的 `done` 一起顶掉**
（§6 第 6 条那个"故意"的语义）。行程状态机把完成契约全押在这个回调上，
回调被偷走之后 `phase` 就永远停在 `returning` —— 而**每个单动作测试都是绿的**。

修法不是改转身语义（那是对的），而是让状态机自己兜底：
`turning/returning` 阶段每 tick 检查"还有转身在飞吗"，没有就把该做的一步补上
（`turning` 补重发这一转，不硬迈步；`returning` 直接收工）。
另外给这条路径加了**具名回归锁** —— 模糊测试换个种子就可能不再命中，卡死必须点名测住。

前三条的修法合成一条原则：**凡是"外部能把窗口挪走"的入口，都要重算或作废目标点**。
`place_default()` 现在先 `walker.stop()`；`set_size()` 现在补 `_clamp_to_screen()`；
`tick()` 每帧用当前尺寸重夹目标，并改用"朝目标取 min/max"推进纵向，
保证目标被夹到身后时也必然收敛而不是走出屏幕。

**顺带一条性能教训**：矩阵第一次跑把整轮冒烟从 70 秒拖到 **8 分半**。
我按"tick 数 × 单价"推算只该多 70 秒，对不上，于是实测各操作单价：
空转 tick 0.41 ms、一次完整行走 24 ms、**一次改尺寸 13 ms**
（`drop_scale_cache()` 之后每帧都要重新缩放 768→420）。矩阵里尺寸随机在 80~420
之间反复跳，缓存被反复清掉，十多万 tick 全砸在大图重缩放上。
解法不是砍覆盖率，而是**矩阵只测状态机不变式，整段静默渲染**
（临时把 `store.pix` / `frame_pix` 换成 1×1 空图）。代价从 8 分钟降到 **2 秒**，
144 组 + 300 链一条不少。渲染路径另有 `render_check.py` 与
"切换尺寸后 pixmap 非空"覆盖，所以并没有少测东西。

### 12.9 随机概率不能读权重，只能量时间占比（v0.11）

用户："各项随机概率也要核查优化。" 一查发现**配的概率根本没在起作用**，三层各有一个原因。

**先造尺**：`tools/behavior_check.py` —— 跑 N 条种子的长时间仿真，把"挑中什么"
和"她实际有多少时间在做这件事"分开量。权重是**挑中**的概率，时间占比还要再乘单次时长：
`roam:sit = 3:2` 看着是 60/40，但坐一次约 15s、走一次约 7s，真实时间占比是 21% 坐着 / 8% 移动。

**① 我自己的第一版量法是错的。** 我用"和上一次不同才记一笔"来构造挑选序列 ——
那等于先把连续重复折叠掉，再宣布"连续重复率为 0"。那是在量自己构造的序列，不是量她。
改成按 `behaviors.fired` 的增量数真实挑选次数。**指标先自证，再拿来说事**。

**② `pick()` 把上一轮那个"踢出候选"，两类候选时就等于强制交替。**
候选只剩 roam/sit 时，"不许连着两次同一个" ⇒ 必须严格交替 ⇒ 重复率恒为 0，
而且 `rng.choices` 的权重**完全不参与结果**（实测 roam/sit 各 50.0%，配的是 3:2）。
改成**降权**（`BEHAVIOR_REPEAT_PENALTY=0.35`）：既留住"别连着五次都在走路"的原意，
又让分布重新由权重决定，还允许偶尔连做两件事 —— 那才像活物。

**③ 冷却从"动作开始"算，长动作会吃掉自己的冷却。** 坐下整段约 21s，45s 冷却只剩 24s
落在她起身之后；走路整段约 7s，30s 冷却剩 23s —— 两者几乎相等，于是"刚做过的那个一定还在冷却"。
改成**从收尾开始算**（在 `tick()` 的下降沿设 cd），配置的秒数才终于等于"做完之后歇多久"。

**④ 冷却值恰好等于平均间隔，于是冷却替权重做了决定。** 间隔 15~45s（中位 30s）
配 roam=30/sit=45 的冷却 ⇒ 每次挑的时候刚做过的那个几乎必然还在冷却。
冷却的语义应该是**兜底**（别在几十秒内把同一件事再来一遍），不是主调度器；
现在全部压到间隔中位数以下（12/25/25/15）。

**A/B 实测**（8 种子 × 1 小时，"重复率"= 连着做同一件事的比例）：

| 配置 | 开关关 | 开关开 |
|---|---|---|
| ① 旧：踢出候选 + 冷却从开始算 + 30/45/50/40 | 0.6% | 0.0% |
| ② 只把 pick 改成降权 | 10.8% | 4.9% |
| ③ 只改冷却（时机 + 数值） | 0.8% | 0.3% |
| ④ 两处都改（现在） | **27.7%** | **11.3%** |

② 和 ③ 单独做都不够（③ 几乎不动重复率，因为它只解开"谁可选"，没解开"只能选另一个"），
两处一起改才让权重生效 —— 这条只有跑 A/B 才知道，靠推理会只改一半。

**⑤ 还揪出一个真 bug：`Crawler.start()` 会谎报成功。** 旧顺序是"先 `enter_posture("prone")`
→ 再 `roam()` → 失败就 `_arrived()` 起身 → **照样 return True**"。两个后果：
观感上她在贴边处"趴一下又弹起来"；统计上行为池把一次什么都没发生的尝试记成"她爬走了一趟"，
实测让 crawl 的挑中占比从权重该有的 27% 虚高到 32%，同时把 roam 压到 25%。
现在拆出 `Walker._roam_target()`，**先确认有地方爬再改姿态**，没地方就直接返回 False
（池子按 1.5s 快速重试，不占用冷却）。

**最终时间占比**（12 种子 × 1 小时）：

```
开关关（出厂默认，只有走/坐）：站着呼吸 70.6% · 坐着 18.9% · 移动 8.2%   94 次动作/小时
开关开（四类）              ：站着呼吸 70.7% · 爬走 7.7% · 趴着 7.5% · 坐着 8.1% · 移动 4.7%
挑中分布 34.4 / 28.5 / 20.0 / 17.2   vs   权重 36 / 27 / 18 / 18   ← 权重终于说了算
平均歇 37.9s 才动一下，最长歇 63s（旧值 81 次/小时、平均歇 45s）
```

顺带调的：`POSTURE_HOLD_S` 从 (8,25)/(10,30) 收到 (8,18)/(8,20) —— 单次 25 秒的坐姿
配上 40% 的挑中率，实测让她四分之一的时间钉在同一个姿势上；下限仍留 8s，
因为坐着微动一轮 2.72s，8s 才够喘满三轮，再短就是"刚坐下就起来"。

冒烟里那条"不会连续两次挑同一个动作（缓冲降级）"原本是**恒真断言**
（用去重后的序列比相邻两项，去重了当然不重复），已换成"重复率必须 >3% 且 <35%"
这条真锁；分布对不对交给 `behavior_check.py` 量（冒烟里几十次挑选，拿它断言分布会偶发假失败）。
另外把派发表收进 `BehaviorPool.actors()` 一个方法，冒烟拿它和 `BEHAVIOR_WEIGHTS` 对账 ——
两边漏一个就是"配了没人做"或"做了没配"。

### 12.10 有目的的行程：走到某处再做一件事（v0.12）

新模块 `trips.py`，两个行程：`edge_sit`（走到屏幕边上坐下）和
`visit_mouse`（走到鼠标底下停住）。**不需要任何新素材** —— 目的地用的是屏幕几何
（边缘、光标），到达动作用的是已有的姿态与朝向。

> **本节记录的是 v0.12 的设计，`trips.py` 已在 v0.14 整模块删除**（用户："把移动的
> 坐下和找鼠标删了"）。留着的理由只剩一条：里面"用户碰过她，未兑现的意图必须作废"
> 与"复用 `Walker.start_to(done=)` 而不是另起状态机"这两条纪律，`Follower` 与
> `PostureWants` 今天还在用。`behaviors.touched` 那个令牌随模块一起删了。

三处设计上的取舍值得记：

- **接法复用 `Walker.start_to(x, y, done=...)`，不另起状态机。**
  `done` 本来就要等"到达 + 转身收尾"全做完才回调，那正是"到了"的语义。
  再写一套"行程状态机"就是和 Walker 抢同一件事的所有权。
- **用户碰过她，目的就作废 —— 而且必须用一个新的计数器。**
  `Walker.stop()` 也会走到 `_end → done`，所以"你把她拖到左边，她因此在左边坐下"
  是默认行为。现成的 `behaviors.quiet` 顶不住：它 6 秒就归零，而一趟行程最长 8 秒。
  所以加了只增的 `touched`，行程发起时记值、到点对一下。理由和 `PostureWants` 的
  TTL 是同一条：**未兑现的意图必须有一个"什么时候不算了"**。
- **`cursor_pos()` 挂在宿主上，`trips.py` 不 import Qt。**
  和 `facing`/`posture` 一样的纪律：能不开 Qt 就能直接跑断言，
  上面那六条行程测试全是在 `FakePet` 上跑的。

**权重是从 2 降到 1 的**：`edge_sit` / `visit_mouse` 各自都含一段走路，
按 2 配上去，实测她的"移动时间"从 8% 涨到 21% —— 加了两个动作就把性格改掉了。
降到 1 之后（12 种子 × 1 小时）：

```
开关关：站着呼吸 64.3% · 移动 16.2% · 坐着 17.0%   86 次动作/小时
开关开：站着呼吸 66.2% · 移动 10.4% · 坐着 10.5% · 爬走 6.4% · 趴着 5.7%
挑中占比 46/27/14/13  vs 本档权重 50/25/12/12      ← 对得上
```

`behavior_check.py` 顺手修了一处自己的错：参照系用的是**全量**权重之和，
可开关关掉时 prone/crawl 根本不可选，于是报出"roam 只占配置的 27%"这种废话。
现在按"这一档真的在池子里的那些"归一。

## 13. 坐姿与趴姿（v0.7）

用户投喂了 8 件新素材：4 张静帧（坐下_正面 / 趴下_正面 / 向左趴着 / 向右趴着）、
4 段视频（坐下 / 趴着转180度 / 向左走_四足 / 向右走_四足），并规定：

- **坐下、正面趴下 = 常驻随机动作**；
- **左右趴着 + 四足走 = 一个总开关后面的随机动作**，且菜单里不给单独选项。

### 13.1 画布必须先加宽（硬阻塞）

管线按高度归一到 `CHAR_H=660`，但同一机位下坐姿/趴姿比站姿宽得多。实测各姿势
归一后需要的宽度：

| 姿势 | 宽高比 | 需要宽 | 旧画布 768 |
|---|---|---|---|
| front | 1.07 | 706 | ✅ |
| **sit_front** | **1.26** | **830** | ❌ 切掉 62px |
| prone_left | 1.20 | 793 | ❌ |
| prone_front | 1.15 | 757 | ⚠️ 只剩 11px |

所以 `CANVAS_W` 768 → **896**（最大需求 + 左右各 33px 余量），`CANVAS_H` 保持 768。
代价是窗口不再是正方形：滑条仍然调**高度**，宽度按画布比例派生
（`PetWindow.pet_w`）。冒烟里"窗口是正方形"那组断言随之改成按比例核对。

### 13.2 通配取文件名差点把整批素材废掉

`POSE_MAP` 原先写后缀（`"正面"` → `glob("*正面.png")`）。新增 `坐下_正面`、
`趴下_正面` 之后，`_正面` 结尾的有三个，**`front` 静默取到了坐姿图**：
内容宽从 706 变 830、站立转身 keys 从 `[1,71,47,28]` 漂到 `[88,71,47,28]`，全程不报错。
改成映射表写**完整文件名** + `pick_asset()` 精确匹配，缺文件直接退出并列出相近文件名。
后缀匹配在这个命名体系下根本无法消歧 —— 不是"下次注意"，是结构上就不该用。

### 13.3 姿态是与朝向正交的维度

`posture ∈ {standing, sitting, prone}`，`facing` 只在**同一姿态内**有意义。
清单里落成注册表：

```json
"postures": {
  "standing": {"faces": [front, side_left, back, side_right], "turn": "turn",
               "idle": "idle_front", "walk": {left, right}},
  "sitting":  {"faces": [sit_front], "turn": null,
               "enter": "sitdown", "idle": "sitdown", "walk": null},
  "prone":    {"faces": [prone_front, prone_left, prone_right], "turn": "prone_turn", …}
},
"gated": ["prone_left", "prone_right", "walk4_left", "walk4_right"]
```

趴着的转身图是**另一条**（`趴着转180度`，实测 keys = 左趴 8 / 正面趴 40 / 右趴 94），
和站立的 360° 不是一回事。

### 13.4 坐下视频不是一段干净的"过渡 + 循环"

逐帧量内容高/顶边/底边（145 帧，内容高 539~570）得到的曲线是：

```
f0→25   570→541  下坐
f30     底边 671→688  前爪伸出来
f70~85  548/122/669 完全静止  一次停顿
f90~115 又涨回 564~569/691  **第二次起身调整**
f120+   回到 546~549  再次静住
```

所以"找尾部稳定带"这个判据**根本不成立**：尾部四分位横跨第二次起身，std 6.4。
按"最后一次越界"算出 `settle=109`（她 f40 就坐下了），
按"全部后续都在带内"算直接退化成 0。两次都错过。
最后换成有物理含义的判据：**下坐是单调变矮，坐定点 = 前 60% 里内容高的最低点**
→ `settle_at=28`，与胶片目视一致。

`PostureHold` 因此是：正放 `[0,28)` 坐下 → 驻留段（**循环范围见 §13.8，不是 `[28,145)`**）→
**倒放回到 0 站起来**（起身不是硬切回站姿）。

> **本节的判据与数字已被 §13.13 取代。** 两点作废：
> ① "下坐是单调变矮，坐定点 = 前 60% 里内容高的最低点"这条判据整条不成立 ——
> 身高对她**往外撇腿**完全瞎，用它选出来的驻留窗口就是用户抱怨的"腿动得太厉害"；
> ② 那些内容高数字（539~570）是在泛洪判据还是绝对阈值时量的，光晕修掉后曲线整体变了。
> 现在三段以静姿图为语义锚点，实测 `enter_at=16 / settle_at=77 / loop=[77,95)`。

### 13.5 四足走素材左右不对称

`向左走_四足` 在画面里**真的平移了 69px**（`向右走_四足` 只有 14px，
现有走路 4~6px）。按 `sequence` 处理会把这 69px 当成"摇摆"保留下来，
观感就是爬着滑来滑去。新增第三种放置策略 **`recenter`**：逐帧水平居中抵消漂移，
但**共用整段缩放**（爬行时的高度起伏是四条腿交替的信号，不能压平）。

### 13.6 四足那一组与总开关（v0.8 交付）

`趴着转180度` 是**线性 180° 弧**（左→正→右，keys `[8,40,94]` 单调递增、末帧就是右趴），
而 `VideoTurn` 整套假设是**环形 360°**：`% cycle`、跨环距离、"绕正面择优"。
直接套会把"从右趴回到左趴"算成绕一大圈前进 11 帧（实际是往回退 86 帧）。

做法是把环形/线性唯一的分歧收进三个钩子，`LinearTurn` 只覆写它们，
按累计视觉路径等分采样、首帧不突跳、中途改道从 `shown` 出发这些全部继承：

| 钩子 | 环形 360° | 线性 180° |
|---|---|---|
| `_distances` | `(tgt-pos)%c, (pos-tgt)%c` | 带符号，往回走就是负数 |
| `_choose` | 取短边 + 平局偏正面 | 只有一条路：朝目标那一侧 |
| `_prefer` | 长度接近时改走"路过正面" | 线性弧上没有"绕正面"这回事 |
| `spin()` | 支持 | 返回 False（180° 弧转不出一整圈） |

**开关的语义**（用户原话："左右趴着和四足走需要打开开关才能被加入随机动作，
并且不会有选项菜单可选项"）落成三层，缺一层都会漏：
1. `posture_faces("prone")` 关掉时只返回 `faces[:1]` —— 朝向表里根本没有被禁姿势，
   `turn_to` 取模也到不了；
2. `BehaviorPool.available()` 把 `crawl` 踢出候选，`Crawler.start()` 自己再挡一次；
3. 菜单只留"四足姿态"这一个复选项，**不给左右趴着与爬走单列任何项**。

**关掉开关时必须当场收场**：`set_quadruped(False)` 若有一段爬走在飞，
先 `walker.stop()` 再 `crawler.stop()`（起身回到站姿），然后才 clamp 朝向索引。
退回旧实现（只 clamp 不停动作）实测会让她**继续用四足步态往前爬**，
而四足步态正是刚被关掉的东西 —— 这条差分用一次性探针验证过，不是想当然。

> **本节第 1 层已被 §13.14 删掉。** 用户后来指出"趴着、四足均应由同一总开关控制"，
> 于是开关的管辖范围从"四足那一组"扩到**整族趴着动作**，`QUADRUPED` 改名 `ALLOW_PRONE`。
> 扩范围之后第 1 层（把趴姿朝向表裁成 `faces[:1]`）就成了纯粹的重复：趴着根本进不来，
> 不需要再在朝向表上挡一次。同一个开关在两层各挡一遍的代价是两层都要维护，
> 漏掉一层就能从朝向索引绕回去 —— 收成一个入口守卫（`posture_allowed`）更简单也更稳。

**趴着期间不许坐下**：`PostureHold.start()` 现在直接问 `crawler.busy`，
不再只靠"walker 忙"间接挡。当前爬走的每一拍恰好都有 walker 在跑，
所以这条今天抓不到 bug —— 它是把互斥关系写明，而不是依赖一个巧合。
（v0.11 补：**这条互斥是"不许同时"，不是"不许点"**。用户点了就得有结果，
所以调用方从"直接 start()、False 就丢掉"换成走 `PostureWants` 队列，见 §13.14。）

**菜单的朝向项跟着姿态走**：非站姿不再摆"正面/左面/背面/右面"。
那四项是站立的朝向表，趴着点"背面"会查到 `prone_right`、点"右面"取模回到正面趴，
等于摆一排指错位置的按钮；而按约定被禁姿势也不该有菜单项。

### 13.7 本轮没做的（除素材之外的两条）

- `walk_toward / walk_away`（正上/正下方走）—— 仍缺素材，见 §6 第 10 行。
- 侧面与背面的待机微动 —— 只有正面有 `静立_正面`。

### 13.8 "坐着"不是一段循环，是三段被误当成了一个动作（v0.9）

用户反馈："坐下保持坐姿的动画也不对，多了一段"。逐帧量内容高与顶边（步长 1，不是之前的 4）
之后，`坐下.mp4` 坐定点之后的真实结构是：

```
f28        642px  ← settle_at，下坐到此为止
f29→30     642 → 662   20px **硬跳切**（素材自己剪了一刀）
f30~66     662 → 673   慢慢抬头伸展
f68~89     652px 连续 22 帧一模一样   完全冻结
f90~118    在 652 ↔ 671 之间来回跳   两个姿态来回抖
f120~144   回到 652 附近，静住
```

也就是说 `settle` 之后**根本没有一段可以循环的"坐着微动"**——
先是一个跳切、一段伸展、一段冻结、一段抖动。
而 `PostureHold` 过去直接把 `[settle, 帧数)` 整段当循环播，
每 4.7 秒就把"伸展 + 抖动"完整重演一次。用户看到的"多了一段"就是这个。

**修法**：管线新增 `loop_range()`，只接受**与坐定帧连续**（高度差 ≤4px）
且自身稳定（同判据）的最长一段作为循环；找不到就退化成"停在坐定那一帧"。
坐下素材实测退化 → `loop=[28,29]`，坐着就是安静地坐着。

写这条的时候我一度想保留一点微动（比如去 f68~89 那段取循环），
但那段与坐定帧差 10px，接上去就是每次进驻留都跳一下 ——
**"有一点动"不如"不动"，动错方向是负资产**。素材换成干净的循环段时代码会自动用上。

> **本节已被 §13.13 取代。** 上面那些高度数字是在"泛洪判据还是绝对阈值"时量的，
> 光晕修掉之后曲线整体变了；而且"找不到干净循环所以停在单帧"这个结论是错的 ——
> 素材里确实有一段 18 帧的安静待机，只是**内容高这个判据看不见腿部**。
> 现在三段全部改以静姿图为语义锚点，`loop_range()` 与 `settle_index()` 都已删除。

### 13.9 向左走_四足 是废素材：她自己走出了画面（v0.9）

胶片图（`tools/strip_check.py`）一眼可见：第 72 帧起她的脸被源画面左边缘切掉，
到 f96 少了半张脸，前景面积从 100% 掉到 **70%**。相邻帧差在 f72 是 1002，
而全段其它位置最大只有 284 —— 一个 5 倍的断崖。

**为什么不能"截掉后半段"救**：量了自相关，`walk4_left` **根本没有步态周期**
（相关峰≈0，任何截断点的接缝差都是段内相邻帧差的 9~12 倍）。
这段视频是"她从画面右侧横穿到左侧"的一次性平移，不是循环走路动画，
所以截到任何前缀再接回起点都是一次硬跳。

**管线侧改成能自动报出来**（而不是等人眼看）：`src_clipped` 字段，
判据是"前景贴到源画面外沿 8px 带 **且** 该帧前景比整段中位少 8%"。
两个条件缺一不可——第一版只查贴边时 `趴着转180度`(21帧) 和 `向右走_四足`(23帧)
也被报出来，但那两段逐帧目视完全干净，只是尾巴快扫到边；
加上面积条件后只剩 `walk4_left` 真阳性。
另注意检出带**必须宽过 `CHOKE=2`**：内收会把被切的那条边一起吃掉，
第一版取 2px 时全表恒为 0，等于没测。

**待办**：向素材侧要一条重新生成的 `向左走_四足`，要求
**角色在画面里保持居中、不许平移**（`向右走_四足` 漂移只有 14px 所以是好的）。
在那之前四足开关默认关，且往左爬会用到这段废帧——**开关别开**。

### 13.10 跑步：不是"另一个动作"，是"这趟太远所以换快步态"（v0.9）

新素材 `向左跑 / 向右跑` 到货后先用 `tools/source_check.py` 体检（见 §13.11 的由来），
结论是两条都干净可用：

| 素材 | 帧 | 漂移（趋势+摆动） | 步态周期 | 首尾接缝 | 背景 |
|---|---|---|---|---|---|
| 向右跑 | 97 | 17px = **0px 趋势** + ±4px 摆动 | 13 帧 | 0.25× | 252 |
| 向左跑 | 97 | 12px = 1px 趋势 + ±3px 摆动 | 18 帧 | 0.34× | 248 |
| 向左走_四足（对照） | 97 | 69px = **55px 趋势** + ±13px | 量不出 | 24.4× | 249 |

跑步素材**没有平移**，所以用 `sequence`（保留那点身体起伏），
不要像四足走那样 `recenter` 抵消掉。

**接法**：跑和走是**同一趟行程的两种步态**，不是两个动作。
`postures.standing` 多挂一张 `run` 表，`Walker` 在 `_begin` 里按
"这趟按走路的步子要走几秒"决定用哪套（`RUN_FROM_S=7.0`）。
判据用**时长**不用像素：像素随显示尺寸变，"要走 5 秒以上就该跑"才是人对远近的直觉。
门限是照着 roam 的目标分布定的（实测 roam 横向位移 168~292px = 走路 4.5~8s），
取 7s 让其中约两成变成跑；取 4s 的话几乎每次都跑，跑就不再是点缀了。

三条刻意的边界：
- **菜单"向左走/向右走"永远只是走** —— 按钮文案和动作不能对不上；
  要跑用新增的"跑向远处"。自发漫游则按远近自动选。
- **趴着绝不升级成跑**：四足没有跑的素材，`_pick_gait` 先看姿态。
- **每跨一步的推进量**：走路 3px/帧×24 帧周期 ≈ 36px，跑步 5px/帧×13~18 ≈ 42px。
  步子更大才叫跑；只是"原地抖得快"就白换了。

### 13.11 转身图的姿势顺序必须与姿态 faces 同序（v0.9 修的真 bug）

`facing.value` 是**姿态 faces 列表的下标**，而 `VideoTurn.start()` 拿它去索引
`keys[to]`。所以 `TURN_POSES[turn]` 必须和该姿态的 `faces` **同序**。

站立两张表恰好同序（正→左→背→右），所以一直是对的；
趴着的转身图当初按**视频播放顺序**写成了 `[prone_left, prone_front, prone_right]`，
而姿态 faces 是 `[prone_front, prone_left, prone_right]`。于是：

| 动作 | 想要 | 实际 |
|---|---|---|
| 趴着"向右看"（索引 2） | prone_right | prone_right ✅（两张表里"右"都排最后，**恰好对**） |
| 趴着"向左看"（索引 1） | prone_left | **prone_front** ❌ |

后果就是**她面朝镜头往左爬**。而且它躲过了此前所有断言——
因为唯一被跑到的那条路径恰好是"碰巧对"的那个索引。

修法三件：① `TURN_POSES["prone_turn"]` 改成与 faces 同序（keys 随之变成 `[40, 8, 89]`
这种非单调序列，无所谓——`LinearTurn` 算距离用的是真实帧号，不看 keys 的排列）；
② 管线加 `check_registry()`，两张表顺序不一致就**直接退出**，不产出清单；
③ 冒烟对每个姿态断言 `anim(turn).faces == posture.faces`，并且**逐方向**转一遍验落点。

### 13.12 顺带修掉的两个小毛病（v0.9）

- **单击换朝向会"死点"**：`CLICK_CYCLE=[0,3,2,1]` 是按站姿四个朝向写的。
  趴着只有 3 个朝向时索引 3 被取模成 0，而她本来就在 0 —— 点一下没反应。
  现在循环序列按当前朝向数截（`_seq()`），只剩一个姿势时 `cycle()` 直接返回 False。
- **四足开关关掉时调度器还握着被禁姿势**：朝向集裁到 1 个只是"索引到不了"，
  但 `VideoTurn.start()` 是 `to % len(keys)`，keys 表里那几个被禁姿势照样能被取到。
  现在朝向数 <2 的姿态直接换 `InstantTurn`。

### 13.13 "坐着"重切第二版 + 一把量接缝的尺（v0.10）

用户第二轮反馈：**"坐下的动画还是不对，腿动的太厉害了，原视频素材是有坐下的动作和坐下待机的
样子的，现在的动画前面多了一点，后面好像少了一点。并且，不同状态、动作不能很好的衔接"**。

这一句里有四个独立的缺陷，逐个量出来才知道各是什么：

**① "腿动的太厉害" —— 驻留段的判据对腿部完全瞎。**
`loop_range()` 用的是**内容高**，而她"把两条腿往外撇"的时候身高几乎不变。
实测旧窗口 `[28,49)` 内平均每帧变化 **1.19 灰阶**，视频结尾真正的安静待机只有 **0.21~0.34**，
差 3.5~5.7 倍。换判据：素材里明摆着给了 `坐下_正面.png` 这张"坐着长什么样"的静姿图，
**拿它当语义锚点**（`front.png` / `sit_front.png` 两端），不再从曲线形状猜动作。

**② "前面多了一点" —— 进入段从素材第 0 帧开播，而那几帧她只是站着。**
更糟的是 `sequence` 模式整段共用一个缩放（按平均高），素材开头的站立帧因此比
`正面.png` **高 22px（+3.3%）**，一开场先"长高一下"再坐下。现在 `enter_at=16`
由管线按"整段最像站立图"标出。

**③ "后面好像少了一点" —— 结尾那段真正的坐下待机，一帧都没用上。**
就是 ① 的同一枚硬币：判据选错窗口，窗口就落在撇腿区，结尾反而被丢掉。

**④ 第一版修法自己又错了，值得单独记。**
我第一版把待机窗口写成"坐定之后**最长的连续平静段**"，量出来 `[80,90)` —— 只有 10 帧，
来回一轮 18 tick × 80ms = **1.44s，比呼吸快一倍，观感还是抖**。
错在**目标函数**：素材里根本没有 20 帧不断流的绝对平静段，"最长连续段"优化的是长度，
找到一段短的就停手了。改成**定长窗口 + 最早达标起点**（`HOLD_LEN=18` → 一轮 2.72s，
`HOLD_TOL=1.35` → 起点从 f80 提前到 f77），一次通过。

**⑤ 顺手挖出来的一条：过渡段没按素材帧距播。**
`PostureHold` 每 tick 只推进 1 帧，而 24fps 素材配 80ms 节拍本该走 `stride=2`
（走路/跑步/转身/呼吸全都走 2，只有这里漏了）。三段重切之后过渡段从 28 帧变 61 帧，
逐帧播就是**坐下要 5.1 秒**；按帧距播 = 2.48 秒，正好是素材自己的时长。

**⑥ 交接点必须落在待机窗口的第一帧。**
"坐到位"（f53，最后一次进入坐姿带）之后还有 24 帧收腿微调才到安静段。
一到 f53 就跳进窗口，那 24 帧被剪掉，实测跳变 4.98 —— 就是"坐下去那一下闪一下"。
现在 `settle_at` 直接等于 `loop[0]`，交接处实测 **0.17 灰阶**，比相邻帧的自然差（0.55）还小。

**"衔接不平滑"这类反馈没法直接改，先造尺。**
新增 `tools/seam_check.py`：桌宠每一帧只可能来自四个地方（静姿图／转身／步态／姿态过渡+驻留），
换来源的那一下就是接缝，40 处全部量成同一把尺，并标出刻度
（0.55 = 相邻帧自然差、4.04 = 产品里已存在且用户没抱怨过的接缝、19~31 = 一次真正的姿态变化）。
有了刻度才知道哪些该修：

- 走路起步/收步 1.6~3.9 → **低于基线，不用动**（原本打算做"收步踩回标准相位"，量完发现没必要）
- 转身 1.8~2.6、呼吸进入 4.04 → 正常
- 跑步起步：`gait_phase` 标定后 `run_right` 从 13.8 降到 11.2 —— 但**地板就是 11.2**

**中途证伪掉一个猜测，省下一次 13 分钟的白重建。** 我原以为 `run_right` 那 12 是
"水平锚点没对齐"，写脚本模拟"逐帧水平居中"后重算：**11.18 → 11.66，反而更差**。
再量宽高比：`向右跑` 0.992 vs `右面` 0.942，而 `向左跑` 对 `左面` 只差 2.0 ——
是**素材左右画得不一样**，不是放置规则错。缩放也救不动（整段 ×0.98 最好 8.6）。
同理 `坐下.mp4` 站立段比 `正面.png` 宽 44px、高 10px。**这类差异管线改不了，只能提素材需求**，
已按实测数字写进 素材规范 §3"同一角色的所有素材必须是同一张身体"和 需求清单 X-32。

**最后仍然要目视。** 数值全绿不等于看着对（§6 第 15 行的教训），所以留了两张图：
`docs/preview/sit_hold_compare.png` 把 `坐下_正面.png`、旧窗口的 f28/f38/f48、
新窗口的 f77/f86/f93 和素材结尾 f144 并排 —— 旧窗口那三帧她在抬爪扭头，
新窗口四帧几乎同一张脸，且和素材结尾那帧（用户说的"坐下待机"）一致；
`docs/preview/sit_cycle.png` 则是运行时**实际显示**的那串帧号（过渡段按 stride=2 取样）。

**顺带修掉一个一直在坏的用户入口**：`启动薄荷猫猫.bat` 是 LF 换行。cmd.exe 解析 LF-only
批处理会把 `rem 无黑框启动…桌宠` 这一行和下一行 `cd /d` 粘在一起，报
"'…桌宠cd' 不是内部或外部命令"，于是**双击它其实从来没启动过桌宠**（此前每次都是我从命令行拉起）。
改成 CRLF 后实测能正常启动。教训：**面向用户的启动入口必须用用户的那条路径验证一次**，
"我能跑起来"不等于"他能跑起来"。（另记一句免得有人重复排查：从本 CLI 里用这个 .bat 拉起来的
桌宠会随命令结束被回收，双击则不会 —— 代理侧要用 `Start-Process` 才能把她留在桌面上。）

### 13.14 菜单、总开关与"点了没反应"（v0.11）

用户一口气提了四件事，其中三件是同一类毛病的不同表现：**同一个规则在好几层各说一遍，
说法还不一样**。

**① 走完面向哪 —— 两条路径两套语义。** `向左走/向右走` 走 `Walker.start()`，
`home` 留空 → `_finish_trip` 回落到"出发前朝向"；`随便走走/跑向远处` 走 `roam()`，
写死回正面。于是"勾左面 → 向右走"走完，她自己又转回左面。
修法不是给 `start()` 补一个默认值，而是把默认收进 `_begin` 一处（`WALK_HOME_FACING`），
顺手删掉 `_finish_trip` 里那条"home 为 None 就用 back"的兜底和已经没人读的 `self.back` ——
**留着第二条兜底，下次就又是两套语义**。

**② 趴着期间点"坐下"静默没反应。** `PostureHold.start()` 见别的姿态占着就 `return False`，
菜单不置灰也不报错，用户完全不知道刚才那一下发生了什么。
改成**意图队列** `PostureWants`：能立刻做就立刻做，做不了就存一个意图，每 tick 试探。
三个设计点值得记：
- **不让 holder 互相打断**。看着最直接的写法是"坐下时把趴着的 stop() 掉"，
  那会把"谁该等谁"写成 holder 之间的递归，而且 `_leave()` 是异步的（要倒放 2.4s），
  当场 stop 完不了。
- **必须有 TTL**。挡着她的东西不止另一个姿态（走路、转身、爬走都挡），
  没有期限的话一个意图能悬几十秒，然后在她完全没预期的时刻突然坐下 —— 那是惊吓不是响应。
  上限 3.0s 是按"她把手上那件事做完"的最长正常耗时定的：起身倒放 2.4s + 一次 90° 转身 0.72s。
- **用户一上手就作废**。拖起她的瞬间清掉队列，和 stop 掉走路/驻留是同一个理由。

队列单独成类而不是长在 `PetWindow` 上，是为了**不开 Qt 就能测**这套"存意图 + 期限 + 试探"
的逻辑 —— 测试替身和真窗口共用同一份实现，不是各写一份。

**③ 总开关管到哪。** 用户："趴着、四足均应该由同一总开关控制啊。"
原来 `QUADRUPED` 只管四足那一组，正面趴下是常驻的，规则散在三层
（朝向表裁短 / 随机池踢出 / 菜单不摆）。扩成 `ALLOW_PRONE` 管**整族**之后，
"裁朝向表"那层直接删掉——趴着根本进不来，不需要在朝向表上再挡一次。
现在只有一个入口守卫 `posture_allowed()`，菜单、随机池、`PostureHold.start()`、
`Crawler.start()` 都问它。**同一个开关在两层各挡一遍的代价是两层都要维护，漏一层就能绕回去。**

**④ 菜单混乱的根因是标题和内容不符**：子菜单叫"走路"，里面却装着"跑向远处"。
改成 `移动 ▸ 随便走走·跑向远处 ── 向左走·向右走`，分组按**目的地谁说了算**，
不按步态。开关挪到紧挨"姿态"的位置，因为它是"姿态能不能做"的前提。
"趴下"这一项在开关关掉时**根本不摆**，而不是摆一个点了没反应的项。

**⑤ 速度：素材只给节拍，不给步幅。** 用户提醒"你要自己看了素材再调"。
看了胶片才确认：`向右走_四足` 是压低身子的四足趴伏，前脚伸出很短，
而它一个步态周期 22 帧、走路 23~25 帧 —— **节拍几乎同频却同速度**，
就是"压着身子走出散步的步子"。
中途两次想用测量代替目视都失败了：先量"底部脚带重心的水平扫幅"，
再量"前缘伸出幅度"，两组数字在左右两条同类素材之间差 4~7 倍
（`walk4_left` 129px vs `walk_right` 5px），因为**长毛把脚掌整个盖住**，
量到的其实是尾巴和毛边在晃。所以这里只认"节拍相同 + 姿态更低 → 步幅更短"，
取 `CRAWL_SPEED=2`（走路的 2/3）。跑步保持 5：它的实测周期是走路的 1.3~1.9 倍频，
现在的 1.67× 正落在里面，这条有数据支撑，不用改。

### 13.15 "有时候有的动画会抖动"：三种病因只有一种能修（v0.11）

抖动这句话有三个可能的出处，分别在三个地方，不量就分不清：
**① 素材自己抖**（生成视频里身体逐帧乱跳）、**② 管线放抖了**（每帧单独算锚点/缩放）、
**③ 运行时节拍撞车**（stride 与循环长度不成整除、循环接缝）。

新增 `tools/jitter_check.py`。**判"抖"要看方向翻转，不是幅度**：一条平滑的大摆动是"走路"，
一段小的高频反转才是"抖"。主指标 = 相邻两步运动方向相反的比例
（正弦摆动约 0.1，纯噪声约 0.67），配上换算到**桌面屏幕像素**的摆幅一起看。

> 这个指标第一版也是错的：用的是 `mean|Δ²| / mean|Δ|` 比值，量出来十条动画全都 1.0~1.6，
> 一律判成"高频反转为主"。因为质心位移本身只有 0.4px，比值放大的是四舍五入噪声。
> **指标本身要先被证明能分开"抖"和"不抖"**，否则它给出的结论比没有结论更糟。

量完的结论：

| 动画 | 屏幕摆幅 | 翻转率 | 判定 |
|---|---|---|---|
| 向右跑 | 0.59px | 0.58 | 真抖（头顶摆幅 0.81px） |
| 向左跑 | 0.17px | 0.54 | 亚像素，看不见 |
| 其余八条 | 0.08~0.33px | — | 亚像素，看不见 |

**① 向右跑的抖在源视频里就有**：直接量原始帧，头顶逐帧位移 `向右跑 4.68px` vs
`向左跑 1.88px` —— 同一条管线、同一套锚点规则，差 2.5 倍只能是素材。
它和 X-32 里"向右跑与右面画得不是一套"是同一条废素材的两个症状。

**② 没有"某帧画坏了"这回事。** 我本来准备做单帧尖峰抹平，判据是"两边邻居彼此很像、
而中间这帧和谁都不像"。跑完是**十条动画全部 0 个候选** —— 每一处大跳的邻居彼此
也同样大跳（`f95: 与邻居差 24.7 / 邻居互差 24.8`）。所以那不是尖峰，是**循环接缝**。
这个判据当场证伪了我自己的修法，省下一次错误的抹平。

**③ 真正能修的是四足走的循环接缝。** 沿"运行时实际播放顺序"量相邻两帧的画面差：
`walk4_right` 最大 16.2 = 中位 5.77 的 **2.8 倍**，`walk4_left` 24.75 = **4.8 倍**。
爬着爬着每 7 秒"咯噔"一下，就是这个。

修法 `gait_window()`：**两层搜索** —— 周期数从多到少试，每个长度再试所有起点，
取第一个接缝达标（≤2.5×）的窗口。只截"最长整数周期"不够：四足走截到 4 个周期
（88 帧）接缝仍有 9.5×，退到 2 个周期（44 帧）才降到 2.05×。
反过来也**不该一味求短**：向左走整段接缝本来只有 1.53×，截到 4 个周期是降到 1.09×，
但两个数字都远在"看得见"以下，代价却是白丢 21 帧素材。
所以加了门槛：**接缝超标（>2.5×）才截**，且丢掉的不超过留下的一半。

顺带修掉一个同源的老问题：起步相位 `phase0` 以前是在**整段**里挑的，
窗口一挪，它可能落在窗口外，运行时 `(phase0 - lo) % n` 会把她第一帧就送到循环另一头。
现在只在窗口内挑。

### 13.16 开关收回、两个新素材，以及"工具自己也在撒谎"（v0.13）

这一轮做了四件事：把 v0.11 扩过头的开关收回来、接入 `正面趴着.mp4` 与
`微笑拥抱.mp4`、给一次性动作开第四个执行者，以及**按用户纠正把"趴着睡"从趴姿里拆出来**。
过程中抓出**四个"指标/工具自己不对"**的问题，比功能本身更值得记。

**① 开关的管辖范围按用户原话收回**："趴下的开关控制是否允许**向左或向右**趴下的
相关动作发生"。v0.11 我把它扩成管整族趴着（含正面趴下），是拿一句有歧义的话往大了解释。
现在 `SIDE_PRONE` 只管三样：`prone_left` / `prone_right` 两个朝向、`prone_turn`、
以及要用这两套朝向加四足步态的 `crawl`。落点仍然只有一处（`posture_faces()` 裁表），
`collapse_prone()` 换成 `settle_side_prone()`：**从侧趴退回正面趴，而不是把她拽起来**。

**② `posture_faces()` 有一条静默漏裁的路径。** 它写的是
`manifest.posture_faces(posture or self.posture)`，但下一行的判据用的是**形参**
`posture == "prone"` —— 不带参数调用时形参是 `None`，判据恒假。`current_pose()`
恰好就是这么调的。新增的断言一跑就红：朝向表返回三个姿势而 `facing.count` 是 1。
先改成"形参为空就先落到当前姿态"再裁。**同一条规则只在两处写，其中一处用错了变量名，
就不报错、只漏。**

**③ 一次性动作是第四个执行者，`Facing` 的回调会被偷走。** `OneShot` 与
`PostureHold` 的区别是**没有驻留**：转回正面 → 正放一遍 → 交还。
`Facing.turn_to()` 不带 done 时会把上一个调用者挂着的 done 一起顶掉（故意的语义），
`Walker` 早就有 `_guard_stolen_callback()` 兜底，`OneShot` 没抄这一条 ——
随机长链实测 **230/300 条收不了尾**，因为她永久停在 `turning`，而 `busy` 永远为真。
补上同一条兜底（转身已落地却没收到回调，就重新发起这一转）。

**④ `behavior_check.py` 自己犯了它所负责抓的毛病。** 它设的是 `pet.allow_prone`
—— 一个已经改名的属性。Python 只是新增了个字段，于是"开关打开"那一档里爬走
从来没被挑中过，**两档报表几乎逐字相同**，而看起来完全正常。改成 `side_prone` 并加一条
起步自检（`available("crawl")` 必须等于传入的开关值）+ 一条产出量断言
（关掉 0 次 / 打开 382 次）。**随机系统的报表必须有"它真的做了"这一栏**，
不然它测的是自己的假设。

**⑤ 我在 `actions.py` 里写过一个没量过的数字。** 注释写"首尾接缝是相邻帧差的 4.0 倍"，
实际把 `seam_check.py` 扩到覆盖两条新素材之后量出来是 **2.9 倍**（11.29 vs 3.86）。
结论方向没错（确实接不上，只能正放一遍），但**写进代码的数值必须是测出来的**。
`seam_check.py` 现在覆盖 49 处接缝（新增趴睡进入/来回一轮最大一跳/退出最坏帧、
拥抱首尾/进出/中途最坏点，以及"趴睡↔趴坐"的跨体对照；超标从 16 处涨到 22 处，
其中 5 处来自两条新素材、1 处是趴睡与趴坐的身体差），下一批素材会自动复检。

**⑥ 我把"趴着睡"接错了姿态，是用户纠正的。** 用户原话：**"趴着睡是完全趴着，
左右那个趴着是趴坐着。"** 这不是同一姿态的两张脸，而是**两种身体**：`prone_front.png`
是趴坐 —— 上身撑起、后腿往前撇开露脚掌；`正面趴着.mp4` 是完全伏地、下巴搁地、闭眼睡。
我此前把后者挂成 `prone` 的驻留微动，结果"正面趴下"看起来在睡、一转到侧面就坐起来，
还把它写成了"素材不一致、待用户定夺" —— 真正不一致的是我的分类。
按用户选定的形态（**单独一个驻留动作**），把它升格为独立姿态 `sleeping`：朝向表只有一个
`sleep_front`，因此转身自动走 `InstantTurn`；静姿图不重出素材，管线新增 `POSE_FROM_VIDEO`，
直接从 `prone_sleep` 第 0 帧导出 `poses/sleep_front.png`（内容高实测 661，不硬凑
`CHAR_H=660`）。`prone.idle` 置空 —— 趴下就是趴坐；池子新增 `sleep`（权重 2／冷却 60s／
驻留 14~32s，"睡一觉"比趴坐久），菜单「姿态」多一项「趴着睡」。改完后 `prone_idle/`
成了无人引用的孤儿目录，`build_assets` 现在会在写 manifest 前按 keep-set 剪掉它，
并在体检里核对每个姿态的朝向都有来源。

**新素材量出来的东西**

`正面趴着`（97 帧）：驻留窗口 `[0,44)`、`loop_stride=2` → 来回一轮 **3.44s**，
窗口内最忙的一帧 2.98、来回最大一跳 3.62，都在基线（4.04）以下；抖动 0.09px／翻转 0.35，
**是全部 12 条动画里最干净的一条** —— 而它恰恰是最常被长时间观赏的那一张
（趴睡驻留 14~32s，比趴坐的 8~20s 更久）。

`微笑拥抱`（76 帧）：抖动 0.78px／翻转 0.61，和 `向右跑` 同一档"看得见的高频反转"，
但它是 3 秒的一次性动作、不是常驻画面，默认尺寸下摆幅不到 1 屏幕像素。
进入 `front→hug#0` 是 11.02（与已接受的"坐下进入 11.82"同档），且开头 8 帧就是全片
离 `front` 最近的一段（再往后是 12~14），所以**没有可裁的起点**。

**拆完再量（`sleep` 独立之后）**：`趴睡↔趴坐`（`sleep#0→prone_front`）差 8.39，
和"站→趴"19.05 同性质 —— 量的是**两种身体的差**，动画里抹不平；`站→趴睡` 22.07、
被打断退出最坏帧 22.31，与"站→坐"27.66 同档（都没有过渡素材）。趴睡驻留本身不受影响：
2.98 最忙帧／3.62 来回最大一跳仍在基线以下。`sleep_front` 深色底无光晕、底边钉死 743
（包围盒 y83，比其它静姿高 1px，来自素材本身）。随机池里 `sleep` 被挑中 13.4%（关）／
11.1%（开），时间占比 7.6%／6.4%，比趴坐（5.1%／4.3%）久 —— 对得上更长的驻留区间。

**概率层复核**（12 种子 × 2 小时 × 两档开关）：挑中占比与配置权重的偏差全部 ≤2 个点
（关：roam 27.0/29、hug 15.8/14、sit 15.4/14、prone 14.9/14、sleep 13.4/14、
visit_mouse 6.9/7、edge_sit 6.7/7；开：roam 22.3/24、crawl 17.8/18、hug 13.0/12、

趴着驻留 4.3~5.1%、四足爬走 4.6%（开）、坐下过渡 2.2~2.6%、拥抱 1.0~1.2%、跑步 0.6~0.7%。

### 13.17 第二次纠正素材分类，以及"能跑但转错方向"的三处管线缺陷（v0.14）

用户这一轮的反馈原话是：**"打瞌睡也加上；左右趴着睡觉也加上，受趴着开关约束；
把移动的坐下和找鼠标删了；姿态的趴着睡没动作啊，还是不对啊，接着修，是不是叫打瞌睡啊，
如果开了趴着的话，是不是再显示一个趴下睡觉啊；抱抱也应该是姿态里面的啊，
而且抱还没扣干净、有抖动；再加个跟随鼠标开关；再全面检查一遍各项。"**

**① 我把 `正面趴着.mp4` 又认错了第二次。** v0.13 我以为"完全趴着 + 闭眼 = 趴着睡"，
把它整个当成了睡姿素材。这次逐帧看下来：那条素材里她**眼睛是星星眼、嘴在一张一合**，
是醒着趴坐的呼吸微动；真正闭眼的是 `向左/向右趴着睡觉`（侧躺、身体完全贴地），
而 `打瞌睡` 是**坐着**打盹（上身直立、头一点一点）。三条素材是三种身体，
我此前只认出两种。最终分工：

| 姿态 | 朝向 | 驻留微动 | 受 `SIDE_PRONE` 管 |
|---|---|---|---|
| `prone` 趴着 | 正面 / 左 / 右 | `[prone_idle, None, None]` | 只有两侧 |
| `dozing` 打瞌睡 | 正面 | `doze` | 否（常驻） |
| `sleeping` 趴着睡 | 左躺 / 右躺 | `[sleep_left, sleep_right]` | **整个姿态都是** |

**② 驻留微动必须能按朝向取。** `postures[idle]` 以前只是一个名字，
于是"趴睡有两个朝向"没法表达：拿整段循环当"这个朝向的微动"，
就会把她画成另一个身体（左躺着却播右躺那一段）。现在 `idle` 允许是**与 `faces`
等长的列表**，`PostureHold._loop_anim()` 按 `facing.value` 取，`None` 表示该朝向
没有微动、停在静姿图上。`build_assets.check_registry()` 在开跑前就核对长度对齐、
每个朝向都有来源 —— 配错要当场退出，而不是产出一份"能跑但转错方向"的清单。

**③ 开关要管到"整个姿态"，而不只是朝向表。** 侧躺睡没有正面那张脸，所以关掉开关时
她不该继续躺着。四道一起落：菜单里**没有这一项**（入口跟着开关藏）、
`PostureHold.start()` 再挡一道（随机池和排队意图绕不过菜单）、
`settle_side_prone()` 让在飞的睡姿起身、`wants` 里排队的 `sleeping` 当场作废。
只做其中任何一道都会漏：只藏菜单 → 池子还会自己躺下；只挡 start → 她正睡着时关开关没反应。

**④ 进入侧躺睡要随机挑一侧。** `Facing.set_posture()` 一律把朝向归 0，
而 `sleeping` 的 `faces[0]` 是"左躺" —— 于是每次进这个姿态都朝左，第二条素材白接。
`_begin()` 里加了一条：**没有转身素材且朝向多于一个**的姿态，进入时随机 apply 一个朝向
（有转身素材的不能这么干，那会跳过那一转）。

**⑤ 抠图判据缺了第二档：低饱和浅灰。** 用户说"抱还没扣干净"是对的，而且不止抱抱：
`向右趴着睡觉` 的前景面积是 44 万 px，真身只有 20 万 —— 源素材背景有一圈**渐变暗角**
（中段 234~237，四边 246），离背景 10 级，卡在 `FLOOD_TOL=8` 外，泛洪走不进去，
整片被当成她身体。`微笑拥抱` 身下那摊**地面投影**（225~240）同理，
在深色桌面上就是一摊白雾，而且逐帧忽大忽小 —— 这正是"抱有抖动"的一半成因。
新增一档判据：`BG_GRAY_TOL=30` + `BG_GRAY_SPAN=16`（通道极差仍要小），
**前提不变：只能从四边连通**。所以白毛(248)被暗描边围住仍然安全，
其余 15 段素材面积变化 <1.5%（拥抱只掉 9k px，就是那摊投影）。

**⑥ 画布宽度封顶。** 横躺的身体按 `CHAR_H=660` 归一需要 **995~1094px 宽**，
超出 896 的画布 —— 头和尾巴直接被切，而旧管线只在 stderr 喊一行警告、清单照写，
派生出来的静姿图包围盒是 `(0,85,895,743)`（两头都贴边）才看得见。
现在 `sequence/recenter/head` 三种放置都按 `min(身高归一, CONTENT_MAX_W / (半宽+最大横移))`
取缩放，封顶 848 宽。睡姿内容高因此只有 513~554（`CHAR_H` 的 78~84%）——
**躺着的身体本来就更矮更宽，这是设计如此**，不是基准漂移；
冒烟里把手工静姿图（必须精确 =660）与派生静姿图（按"与源帧逐字节相同 + 不超画布"锁）分开断言。

**⑦ 抱抱的横向抖动不是素材抖，是锚点选错了。** `jitter_check` 量到旧 hug
摆幅 0.78 屏幕 px／翻转率 0.61。逐帧拆开：包围盒水平中心一圈移动 7px，
但**头部只动 1.1px** —— 那 7px 全是手臂开合把包围盒带偏的。
`sequence` 模式按包围盒中心给锚点，等于让整只猫跟着手一起左右晃。
新增 `head` 放置模式：锚点 = `(包围盒中心 − 中位) − (头部中心 − 头部中位)`，
头部钉住、手照样抱。改完 **0.10px／翻转 0.81**（摆幅已在"看得见"阈值 0.6 以下）。
副作用要记一笔：相邻帧差中位从 3.86 降到 0.92，所以"首尾接缝是相邻帧差的倍数"
从 2.9× 涨到 **12.4×**（绝对值 11.40 基本没变）—— 分母变小不是接缝变差。

**⑧ `show_posture()` 写死了 `facing=0`。** 侧趴着驻留时（`idle` 列表里那一档是 `None`）
每一 tick 都会重画 `prone_front` —— 观感就是"趴着趴着自己翻回正面"。
现在默认取**当前朝向**，并且走 `posture_faces()`（顺带修掉它绕过开关裁减、
以及漏掉变体与 `k` 缩放这三处）。这条是补测"趴睡两个朝向各播各的素材"时顺手抓到的。

**⑨ `keep_facing` 的收尾漏撤了在飞那一转。** 跟随的小步走完不转身（每步都转回正面
就是原地拧陀螺），但 `_finish_trip()` 一短路，就把还挂着 `_walk` 的那一转留在了空中：
回调照触发，她朝**出发时算的旧目标**又迈了一步 —— 动作矩阵实测
"跟随开→回到右下角"之后她自己走开 6px。现在这一档改成
`turn_to(self.face, done=self._end)`：把 done 换掉，转完就收工，朝向仍停在行进方向。
（`Walker` 别的路径早就有这条"重新发起一转来顶掉 done"的招，新写的短路又漏了一次。）

**⑩ 删掉两个行程。** 用户点了"把移动的坐下和找鼠标删了"，`trips.py` 整个模块移除
（不是留着不用）：`edge_sit`/`visit_mouse` 的语义已被「跟随鼠标」覆盖得更直接，
菜单里那两条又与"移动"子菜单的分组原则（目的地谁说了算）冲突。
连带删掉 `behaviors.touched` 这个只被它用的计数与 `TRIP_EDGE_PAD`。

**⑪ 跟随鼠标为什么是"一小步一小步"。** 一开始想的是逐帧朝光标挪，实测不成立：
步态最低 3px/帧，逐帧修正就是每秒十几次折返，而每次换向要 0.72s 转身，
她只会原地抖。所以 `Follower` 只做"看距离 → 走一程 → 再看"：
死区 40px（按显示高缩放）挡掉光标附近的抖动，>260px 换跑步追，
纵向仍由 `WALK_SLOPE` 夹（没有朝镜头走的步态，正上方就老实不发起、0.6s 后再看）。
三条让路规则：菜单开着不跟（否则她会跟着光标走进菜单里）、
姿态驻留期间不跟（用户手动让她坐着，她不该自己站起来走）、
跟随开启时随机池**完全让位**（不然刚跟到旁边又自己溜走）。
打开跟随会先把她从当前姿态里放出来 —— 趴睡一驻留就是 30 秒，
不等她起来用户会以为开关坏了。

**⑫ 全面复核时又抓到一条"报告自己在撒谎"。** `向左走_四足` 是已确认的废素材
（§13.9：24 帧被源画面切掉、根本没有可重复的步态周期），但管线的报告一直给它印

### 13.18 用户三条反驳，逐条复现之后发现她全说对了（v0.15）

用户原话：**"跟随鼠标要实时跟随啊，离得远了要跑起来啊，而且为什么正在进行动作时不能
切换到另一个动作，你怎么这样啊，还有的还是抖动，你仔细检查了吗。"**

三条我上一轮都写进了"设计如此"，这一轮逐条复现，**三条都是我的问题**。
记下来是因为它们的错法各不相同，值得分开看。

**① 跟随"一顿一顿"不是节拍的错，是我自己把自己叫停。**
旧 `Follower` 是"发起一趟 → 走完 → 再看一眼"，一程 3~5 秒，这已经慢了；
更糟的是它的让路判据里写了 `facing.turning` —— 而跟随起步的第一步本来就是
"转成侧视"，于是她刚转身就被判成"忙"、`_halt()` 收掉这一转，3 tick 后再重新起步。
trace 一眼看穿：`turning, turning, turning → returning → walking`。
**把"正在做这件事的第一步"当成"这件事被别的占着"，是这类让路判据最典型的错法。**
现在 `_blocked(following=True)` 不再把转身算作阻塞。

**② 实时跟随 = 一程走到底 + 每 tick 改道，而不是小步快走。**
新增 `Walker.retarget(x, y, gait)`：在飞的行程直接把终点挪到光标上，
纵向节拍按"剩余横向还要走多久"重算，方向反了才重新转身，
距离拉开就当场 `walk → run`（不用等下一趟）。
`Follower` 只在死区外发起**一趟**，之后每 tick 改道，进死区就地停（保持行进方向）。
实测 150 tick 长距离跟随**起步次数 = 1**（旧实现每 3~5 秒一次），
光标从右 400px 突然后撤时她改道停在新光标旁边，而不是先把旧目标走完。
死区 40→30px、跑步门槛 260→170px：40px 配上"走完再看"就是用户说的"不实时"。

**③ "点了没反应"是排队期限被用在了两种完全不同的场景上。**
复现出来的两条硬证据：跟随开着点「坐下」，**32 秒都没坐下**（意图被 TTL 丢掉）；
就算不开跟随，漫游途中点「坐下」也一样失败。
`POSTURE_WAIT_S=3.0` 的原始理由是"她把手上那件事做完 ≈ 3.1 秒"，
这个理由只对**自发动作插队**成立；漫游一趟最长 8 秒、跟随是无限长，
于是"用户指令"和"她自己想做的事"共用同一个期限，用户就永远排在后面。
现在 `PostureWants.request(key, manual)` 分两种：
**手动**（菜单点的一律 manual）先让占用者收场 —— 中止在飞的行程、结束一次性动作、
当前姿态转去 `leaving` —— 然后立刻起步；**非手动**（池子挑中的）仍然只排队，
期限从 3.0 放宽到 5.0 秒（覆盖"起身倒放 2.4 + 转身 0.72"再留一半余量，
旧值 3.0 恰好卡在 3.1 上，所以"起身途中点坐下"会差一点点而静默失败）。
一条判据顺带补上：跟随在 `wants` 里有待兑现意图时必须完全让路，
否则她一边排队坐下、一边继续往前走，那个意图又变成等不到。

**④ "还有的在抖"——我的指标把问题盖住了，这次是用户的眼睛比我的表准。**
上一轮我报"抱抱抖动 0.78px → 0.10px，看不见"。那个 0.10 是**逐帧原始序列的平均摆幅**。
两处错：运行时是 `stride=2`（24fps 素材配 80ms 节拍），**抽稀会放大相邻显示帧的跳变**；
而平均数会把一记 3px 的尖峰摊进 60 个显示帧，剩 0.05px。
`jitter_check` 重写为：按运行时真正画出来的那一串帧算（步态窗口 + 起步相位 +
驻留来回折返都建模），主指标从平均摆幅换成**最大单帧跳**。

判据的参照物也换了一次：**包围盒顶边不是她的头**。
跑步时最上面那一行会在头顶、耳朵、甩起来的尾巴之间来回切换，
它跳 3px 不代表身体动了 3px；整幅质心又被伸出去的四肢带偏。
现在量"顶部 35% 那条带的质心"。这条教训同时决定了管线怎么补偿 ——
`bob_dy()` 拿顶边算的第一版，报告写着"8.9→3.6 画布px"，成品量出来**纹丝没动**，
因为 `to_canvas` 是**底边**对齐基线的：内容顶边落在哪由"画布高 − 基线 − 本帧内容高"
决定，高度起伏会自己把顶边推来推去，补偿量必须按"头相对底边"算。
**报告算的模型和产物真实的模型不是同一个，这份报告就是废纸。**

**⑤ 纵向去抖只对位移类动画做（`BOB_ANIMS`）。**
坐着、睡着、呼吸时底边对齐就等于"脚踩在地上"；把头部钉到趋势上，
等于让她的脚每帧离地几像素，还会破坏与静帧的基线对齐（冒烟那条 ±2 帧的
"底边压在基线上"锁会红）。走路跑步本来就有一瞬双脚离地，抬一点是物理正确的，
补偿量仍夹在 8 画布px（≈1.6 屏幕px）以内。
